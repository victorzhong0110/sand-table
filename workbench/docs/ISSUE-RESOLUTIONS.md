## #6 MCP 接入与使用体验

issue 原文承认「问题 A（连不上）」与「问题 B（用不顺）」同源。按原文的四个问题分别落点。

### A 凭据自愈

- **现象**：`connection.json` 里没有的凭据一旦从地址栏消失，页面永久卡在未认证态，只有一句错误提示，没有可点击的恢复入口。
- **根因**：凭据只从 URL 片段读一次，读到就 `history.replaceState` 抹掉；`sessionStorage` 又是每个标签页独立的。新标签页、新导航都取不回来。
- **改动**：`local/client.ts`
  - 接受 `?session=<token>` 作为片段的等价入口（两种写法都能进）。
  - 片段与参数都缺失时，页面自动向本机服务 `POST /session` 取一次凭据（同源 + Origin 校验**没有放宽**），拿到后继续。
  - 取不到时给出**可点击的恢复入口**，而不是一句死提示。
  - 收到 403 时重取一次凭据再重试。
  - 路由按 `pathname` 匹配，不再依赖片段。
  - **页面上已经开着、又贴进一条新链接时，也能自愈**（见下）。
- **验证**：`tests/session.test.ts` 覆盖 `link` 字段的拼装与校验（含非法 link 断言）；`tests/local.ts` 走真实本机服务。

#### 「页面上已经开着，又贴进一条新链接」

- **现象**：地址栏里换一条带新 `#session=` 的链接，页面**不会重新加载**（只有 fragment 变），于是 `local/client.ts` 里的脚本根本不重跑 —— 页面继续用手里那个**已经失效**的凭据，之后每个请求都是 403，页面停在「与本地工作台断开」，只有手动刷新或点「重新连接」才能恢复。
- **为什么它是真实场景**：文档里推荐的启动方式是 `npm start -- --port <固定端口>`，地址在重启后**不变**，变的只有凭据。于是「地址不变、凭据变了」就是常态，**贴新链接进已开的标签页**是最自然的操作。
- **改动**：`local/client.ts` 监听 `hashchange`：片段里带着格式合法的凭据、且与当前用的不是同一个时，**采用新凭据并重连**。若它已经失效，`connect()` 的兜底会向本机服务再取一次当前凭据。
- **验证**（`tests/local.ts`）：用**固定端口**启动 → 重启实例（地址不变、凭据轮换）→ 断言页面出现「与本地工作台断开」→ 把新链接贴进同一个标签页（只改 fragment）→ 断言页面自己恢复，白板重新可用。
  - **反向验证**：撤掉 `hashchange` 处理，这条断言超时变红；恢复后通过。
- **这一条是用产品时撞出来的**，不是事先想到的：把新链接贴进已经开着的标签页，页面直接 403 死在那儿。

### B 读回路径统一

- **现象**：「我到底写没写进去」需要人替 Agent 判断。
- **改动**：
  - `core/results.ts`：`boardSummary` 增加 `instanceCount`，并重写 `hint`（说明 `objectCount` 与 `instanceCount` 各算什么）。
  - `server/spaces.ts`：`sand_find_objects` 同时返回 `objects` 与 `instances`，新增 `instanceType` 过滤 —— 刚建好的组件现在能被标题/type 查到。
  - `server/spaces.ts`：`sand_edit_space` 改用 `viewResult` 返回 `createdInstances` / `changedInstance`。
- **验证**：`tests/blank.ts` 端到端断言（经 MCP 建组件 → 读回 → 撤销 → 重做 → 跳转）。

### C 错误信息指对方向

- **改动**：`local/session.ts` 把错误分流成两类：「会话文件读不到」与「读到但请求被拒（token 过期/端口变了）」，两类都带**会话文件路径**。
- **验证**：`tests/session.test.ts`。

### D 启动不抢浏览器

- **改动**：`local/main.ts` 默认 `open=false`，只有显式 `--open` 才开系统浏览器；终端打印完整链接（含 `#session=`）。
- **验证**：`tests/local.ts`；启动脚本参数转发有单测。

### 额外修的一个真实缺陷（不在 issue 原文里）

**现象**：Agent 在板上写过一次之后，人在界面上点「固定位置」「图标＋标题」这类按钮，**点了没反应**，只弹一条红色错误条「Board changed. Read current board and retry.」；最多要等 5 秒（界面刷新轮询周期）才恢复。

**根因**：界面每 5 秒才轮询一次 `sand_read_board` 刷新自己的 `revision`；在这 5 秒窗口内，界面发出的写操作带着过期的 `revision`，被服务端的乐观并发闸拒掉。

**改动**：`board/main.tsx` 的 `action()` —— 被「Board changed.」拒掉的写，先读一次当前板、拿到新 `revision` 再**重试一次**。被拒的写从未生效，重试不会写两遍。

**这条是自审时从测试失败里挖出来的**，不是事先想到的：#9.5 的 MCP 撤销/重做断言把 revision 顶掉了 4 格，紧接着的界面点击就被拒。

## #9 画布交互

### 1 边缘平移默认关闭

- **改动**：`board/CanvasShell.tsx` 的 `edgePan` 初值 `true` → `false`；设置里的开关与速度项保留。
- **验证**：`tests/blank.ts` 先断言「边缘平移默认不动」，再进设置勾选「边缘移动」，然后断言能平移 —— 默认关与可开启两件事都被断言住。

### 2 选中组件后可直接拖动

- **改动**：`board/SpaceCanvas.tsx` —— 拖动不再要求 `mode === "arrange"`，浏览模式下直接拖就能移动。
  - **点击不是拖动**：指针位移超过 3px 才算拖动（`drag.moved`）。这样点一下组件不会平白写一条新位置。
  - **固定组件**：拖动被固定的组件时，客户端先把 `pinned` 置为 `false`。服务端 `place` 的「pinned 且坐标变化就报错」校验**没有改**，所以客户端发**两个** `place`：先在原坐标解锁，再移动。两个写共用同一个 `intent`，服务端把它们合并成**一步**历史。
  - 界面上有可见反馈（画布左上的提示条：「移动已固定的组件会解除固定」）。
- **验证**：`tests/blank.ts` —— 浏览模式下拖动，断言位置真的变了；固定后再拖，断言位置变了**且** `pinned` 变成 false。

### 3 选中后就地编辑

- **改动**：`board/SpaceCanvas.tsx` —— 双击组件进入就地编辑。有正文的组件（text/heading/code）编辑正文，其余编辑标题。
  - `board` / `space-link` 的双击**仍然是进入子白板**，这个既有行为没动。
  - 编辑态有明确视觉区分（卡片描边 + 编辑框强调色边框）。
  - Enter 提交、Esc 取消、失焦提交。
  - 就地编辑的可访问名是「就地编辑内容」/「就地编辑标题」，**与属性栏的「内容」「编辑组件名称」不撞名**（既有测试靠这些名字定位）。
- **验证**：`tests/blank.ts` —— 双击 → 出现编辑框 → 输入 → Enter → 断言服务端的内容真的变了。

### 4 改完即存

- **改动**：`board/ComponentPanel.tsx` —— 内容字段（标题、正文、以及各类型的纯文本字段）**停止输入 600ms 自动提交、失焦提交、Esc 取消**；「保存组件」保留作兜底；**提交失败有可见反馈，且能看出是哪个字段没存上**。
  - **只回写改动过的键**：提交时把「本地改动的键」合并进**服务端当前的数据**，而不是把整份本地快照写回去 —— 否则 Agent 在同一组件的另一个字段上的改动会被自动保存覆盖掉。
  - **会话边界**：一次编辑会话 = 一个 `intent` = 一步历史。**在同一个组件里换字段不算离开**（否则一次「改标题 + 改正文」会被拆成两步，撤销一次看不见变化）；离开这个组件（选中变了）或按 Esc 才换新的 `intent`。
  - 面板与画布就地编辑共用同一套 `intent`（`board/edit-session.ts`），所以两处编辑是同一步。
  - **提交失败会保留待提交状态**，下一次尝试会重试，不会静默丢内容。
  - 结构化编辑器（清单条目、图表数据、表格行、事件流）仍走「保存组件」按钮 —— 它们的形状由服务端校验，逐字提交半成品会被拒。
- **验证**：`tests/blank.ts` —— 在属性栏的「内容」里填字，**不点任何按钮**，断言服务端的内容自己变了。

### 5 像 Word 一样的回退（且回退本身能回退）

- **实现**：新增 `core/history.ts`（游标模型）。
  - `steps`：追加式的写入链，每步存一份完整内容状态。
  - `flips`：撤销/重做/跳转的**日志**（不是弹栈），带作者标签。
  - `cursor`：当前位置。
  - 撤销把游标往回走一步，**同时往 `flips` 里压一条「撤销了 X」的记录**；这条记录在历史面板里可见、可被再翻转（即「回退的回退」）。
  - 粒度：同 token 的连续写入合并成一步（一次连续拖动 = 一步，一次连续输入 = 一步）。
  - 范围：**只回退白板内容**（instances/spaces/links/groups/placements/packs/theme）。选中、相机、导航是视图状态，不进历史；**intent/proposal/validation 一律不碰**，回退不绕过人确认那道闸。
- **对外**：`Cmd+Z` / `Cmd+Shift+Z`（Windows 为 `Ctrl`）；MCP 侧 `sand_history` / `sand_undo` / `sand_redo` / `sand_undo_to`；`sand_edit_space` 增加 `kind:"undo"|"redo"`。
- **历史面板**：`board/HistoryPanel.tsx`，挂在左侧工具箱的「历史」页签，列出最近若干步（标签/作者/时间），可跳回任意一步，跳转本身也是一条记录。
- **验证**：`tests/history.test.ts` 13 个用例；`tests/blank.ts` 端到端（经 MCP 撤销/重做/跳转）。

#### ⚠️ 与 issue 字面表述的一处分歧（必须写明）

issue 第 6 条的「实现要点」写的是：

> 撤销之后再按 `Cmd+Z`，刚才被撤掉的东西会回来（因为「撤销」本身也被记成了一步，并且可以再被撤销）。

**本实现没有照这句话的字面做**，原因是它与同一 issue 的第 1 条「`Cmd+Z` 覆盖全部写操作」**不能同时成立**：

- 若 `Cmd+Z` 永远翻转「最后一条记录」，那么撤销之后再按 `Cmd+Z` 会把刚撤掉的东西翻回来 —— 那么**连续两次编辑永远无法连续撤销**，人按十次 `Cmd+Z` 只能在一件事上来回横跳。这正是 issue 自己在「实现要点」里担心的「如果实现成撤销 = 弹栈，就永远没有回退的回退」的另一种形式。
- 本实现取第 1 条：`Cmd+Z` **一步步往回走**（覆盖全部写操作），`Cmd+Shift+Z` 往回走一步；被撤掉的那一步可以再被翻回来 —— 走「历史面板里点回那条编辑记录」或 `Cmd+Shift+Z`。
- issue 第 6 条的**实质要求**（「撤销不是弹栈，而是一条记录；它可以被再次回退；它出现在历史面板里；Agent 的回退与人没有区别」）**全部满足**，且有单测断言。
- 若 Vic 认为必须严格照字面走，改动只在 `core/history.ts` 的 `applyFlip` 一处：让 `undo` 在「最后一条记录本身就是撤销记录」时改为前移而不是后移。**这是唯一需要动的地方**，其余（`flips` 日志、历史面板、MCP 工具、粒度合并）都不受影响。

#### 自审中发现并修掉的一个真实缺陷

`core/history.ts` 里，撤销记录原本记的是**步骤在数组里的位置**（`flip.cursor`）。而历史有上限（100 步 / 8 MB），`trim()` 会把最老的步骤从队首挤掉 —— **位置全体前移，记录里存的位置就全错位了**。后果：历史面板里点一条旧的「撤销」记录会跳到**错的步骤**；「当前位置」标记也可能被认领到别的记录上。

- **修法**：记录改记**步骤 id**（锚点），位置只作为给人看的附带信息。`undoTo` 解析时按 id 找当前索引。
- **回归断言**：`tests/history.test.ts` 的「a recorded undo keeps pointing at its step after old steps are trimmed」—— 先把历史填过 100 步触发裁剪，再跳回旧记录，断言落在正确的步骤上。
- **这条断言经过反向验证**：把修复退回旧写法后它变红（12 pass / 1 fail），恢复后 13/13 通过。

## #10 缩放条上的「放大」按钮消失

**结案口径：找到了一个真实缺陷并修掉 —— 「文本太长把按钮挤掉」这个机制是真的；但缩放条本身的那个「放大」按钮，仍然没有复现被盖住。** 两种读法（报告者看到的是缩放条的「放大」，还是卡片自己的层级切换按钮）在没有那张截图之前无法分开，所以下面把两边都写清楚。

### 一、复现并修掉的真实缺陷：长标题在「图标+标题」档把卡片自己的按钮顶出卡片

- **现象**：卡片处于「图标+标题」这一档时，如果标题很长，**标题不截断**（`text-overflow: ellipsis` 根本不生效），并且**卡片自己的层级切换按钮被顶到卡片框外** —— 实测被顶出 **446px**，按钮等于消失了。
- **根因（两层）**：
  1. `.component-chrome` 是**行**方向 flex 容器，标题是它的 flex 子项。flex 子项的 `min-width` 默认是 `auto`，而标题又是 `white-space: nowrap` —— 于是它的最小尺寸 = 全文宽度，**不肯收缩**，ellipsis 因此永远不生效。
  2. 修好第 1 层还不够：`style.css` 里另有 `.component-card strong { flex-shrink: 0; }`（那条是为了让「完整界面」档的标题不被纵向压缩），它的特异度 (0,1,1) **高于** `.collapsed-title` (0,1,0)，会把 `flex-shrink` 又压回 0。所以最终规则必须写成 `.component-card .collapsed-title`。
- **实测对比**（长标题卡片，「图标+标题」档）：

  | 指标 | 修复前 | 修复后 |
  |---|---|---|
  | 标题 `flex-shrink` | 0 | 1 |
  | 标题显示宽度 | 608px（全文铺开） | **150px（省略号截断）** |
  | flex 行 `scrollWidth` | 674（溢出 460px） | **216（无溢出）** |
  | 切换按钮 right / 卡片 right | 1043.7 / 598 | **228 / 240（按钮在框内）** |

- **改动**：`board/style.css`
  - `.component-card .collapsed-title { min-width: 0; flex: 1 1 auto; }`
  - `.zoom { z-index: 5; }` —— 缩放条压在画布内容层之上（`.world` 是带 transform 的层叠上下文），**画布上任何卡片内容都盖不住缩放条**。这是对 issue 尺子「任何窗口尺寸、任何缩放级别、任何面板开合状态下都必须同时可见可点」的直接加固。
- **回归断言**（`tests/blank.ts`）：造一张长标题卡片 → 切到「图标+标题」档 → 断言「标题被截断」且「按钮在卡片框内」→ 再把这张卡拖到缩放条上方 → 断言缩放条 5 个控件仍然可见可点。
- **反向验证**：把 CSS 退回原样，这条断言变红（`A long title is truncated with an ellipsis (title 608px shown, 608px of text)`）；恢复后通过。

### 二、仍然没有复现的部分：缩放条上的「放大」被盖住

- **已排除的**：issue 原文自己列的 8 类原因，我在当前构建上重新过了一遍（4 档视口 × 4 档缩放 × 工具面板开合 × 适应/复位/最小缩放 × 动画中点击），缩放条 5 个控件**始终在 DOM、可见、可点**，`document.elementFromPoint()` 命中按钮自身。
- **补做的三件事（把「是不是另一个构建」这个可能性关掉）**：
  1. **定位到报告者当时那一版构建**：issue 记的现象发生在 **2026-10-20 11:53**，而当时仓库里最新的提交是 `1fe7b71`（10:18），图标按钮那个修复 `8ad933a` 是 **12:18** 才提交的 —— 所以报告者用的确实是 `1fe7b71`（同一轮反馈里「属性栏按钮换行」正是这一版的问题，已由 `8ad933a` 修掉）。

## 新增需求：组件包导入协议

规范在 `workbench/docs/COMPONENT-PACK-PROTOCOL.md`（权威规格），实现在 `core/packs.ts`、`core/pack-fetch.ts`、`server/packs.ts`、`board/Toolbox.tsx`。

### 协议的两条硬规则

1. **组件包是数据，不是代码。** 它只能给**已经存在的组件类型**配预设，永远不能带来新的渲染器。包可以声明一个这一版不认识的类型 —— 数据保留，画布上显示渲染器**本来就有**的未知类型占位（`board/ComponentRenderer.tsx` 里已有的分支），不给它加任何新代码。
2. **预填数据走与编辑器同一个校验函数**（`core/spaces.ts` 的 `checkComponentData`），不是它的复制品 —— 导入不是绕过校验的后门。

### 实现要点

- 清单用 zod 校验；未知字段忽略并提示；重复 key、超限（20 包/板、50 组件/包、256 KB/清单）都拒绝并给中文原因。
- 已知类型的**不认识的键**会被丢弃并提示；**未知类型的键全部保留**（占位展示原样 JSON）。
- 预填数据**先按原样校验、再丢未知键** —— 否则 `{type:"text", data:{url:"javascript:..."}}` 会因为键被丢掉而绕过编辑器会拒绝的检查。
- 取件（`https://` 链接）走 `core/pack-fetch.ts`：只 https；字面 IP 与**解析后**的地址都拒绝回环/私有/链路本地；**每一跳重定向重新校验**；5 秒超时；256 KB 上限；Content-Type 必须是 JSON 家族。
- 导入/移除是白板内容变更 → 进历史 → **可以撤销**（有单测断言）。

### 验证

- `tests/packs.test.ts` 25 个用例（含 SSRF 的三条：私有地址被拒、非 https 不出网、每一跳重定向都重新校验）。
- `tests/blank.ts` 端到端：粘贴 JSON → 导入 → 左侧出现包分组 → **未知类型的提示出现在导入面板里** → 点预设 → 画布上真的多了一个该类型的组件。

### 自审时补上的一个缺口

服务端导入时会返回 `warnings`（例如「未知组件类型「timeline」，数据已保留」），但**界面原来把这些提示丢掉了** —— 协议要求「不静默丢弃」，前端丢掉提示等于静默。现在导入面板会显示「已导入「评审包」，有 1 条提示：……」，`tests/blank.ts` 对这条提示有断言。

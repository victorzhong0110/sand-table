# 默认空白画布的实机验收

本轮界面验收从零工作区开始，不能再用自动铺满源码的代码场景代替。先按下文启动一个新的验收工作空间。应只看到空板、左侧工具箱和少量顶栏操作，不应要求仓库、不应出现代码卡片或项目统计。

1. 不接 AI、不导入仓库：拖一张便签到指定位置，编辑名称与正文，调整大小、固定、复制。选中才出现属性面板。
2. 加入一张白板，进入后添加图表和比较，返回父级；检查包含、独立实例、关系开关、移动和键盘。
3. 添加研究场景，确认它是主动加入而非启动自动生成。填真实数据，切换黑白／纸张／自定义，检查 Mac 中文输入法与缩放。
4. 按下文把本地工作台接入 Codex，直接在 Codex 对话里请它在同一张板添加一张验收便签。检查便签确实出现，人的布局和固定位置不变。无需点「询问选区」或从白板复制提示词。
5. 在左侧「仓库」主动导入外部 Git 根。目录和文件进入索引，根画布不应被源码铺满。按下文核对实际源码，再进行改动验收。
6. 刷新、断开、重连和重启进程，核对同一工作空间中已保存的作品仍在；不要用旧代码界面的测试代替。

以下原有源码、确认与真人评估条目继续适用，但必须在主动导入之后执行。

## 代码领域与宿主接入记录

状态：**真实模型／用户客户端待执行**。本地启动器、浏览器与独立 MCP bridge 的共享会话已自动验证；没有任何商业 AI 客户端在本项目中被记录为通过。此文准备可重复的接入步骤，不能当成完成记录。

## 使用入口：直接在本机 Codex 对话

记录 Codex 客户端及版本、操作系统、模型名称、Sand Table 提交、Node 版本。源码验收另记外部仓库路径、Git HEAD 和是否有未提交变更。使用可丢弃的仓库副本，不使用 Sand Table 或 llm-research-os 本身。

1. 从 Sand Table 根目录启动一个新工作空间。下例适用于 macOS / Linux；每轮用新的后缀，重启时复用本轮的目录、工作空间和会话文件：

   ```bash
   npm start -- --workspace-id host-acceptance-01 --session-file "${TMPDIR:-/tmp}/sand-table-host-acceptance-01.json"
   ```

   保持终端运行，用打印的完整链接打开本机浏览器。链接包含凭据，勿写入报告或分享。若此前已把名为 `sand-table` 的配置用于日常工作，安装测试配置时先把生成命令中的服务器名换成 `sand-table-acceptance`，以免替换原配置。
2. 在白板「帮助」中找到「Codex CLI 安装命令」，只在本机终端执行一次。用 `codex mcp list` 核对注册，并在同一台机器新开 Codex 对话。配置指向刚启动的本地工作台，不要另启原生 stdio 源码服务器来连接这张板。
3. 在 Codex 对话里输入下面的请求。让它在实际的 MCP 调用中读取当前白板，而不是粘贴选区或让 Codex 用文件系统猜测白板内容。若当次对话没看到工具，先核对会话文件路径及工作台是否仍在运行，再重开 Codex 会话。仅能接远端 HTTP 的客户端不适用于此路径；不要把本地服务暴露出去。

可再绑定另一个外部 worktree 核对来源，分别记录工作空间、仓库和对象编号。若测试原生内嵌 MCP App，使用该宿主支持的配置，单独记录 App 是否呈现；Codex 文本会话加独立浏览器不算原生 App 通过。DSH 的真实模型与白板内提交另按 [T66](../../docs/kernel-v3/tasks/T66-dsh-device-check.md) 记录。

## 第一段：连接与来源

在 Codex 发出：

> 用 `sand_status` 确认你连接的是哪张 Sand Table 白板，报告工作空间 ID、首页白板 ID 和修订号。先不要写入。

记录真实工具调用和结果，核对新建空间、首页白板及修订号。接着在浏览器的「仓库」导入外部 Git 根，回到同一 Codex 对话：

> 用 Sand Table 查找已导入的仓库、README 和一个索引到的入口函数。先用 `sand_query` 找对象，再用 `code_repo` 的 `read_source` 读取摘录。说明文件和行号、哪些结论有源码依据、哪些范围没索引或没读。不要修改、安装或执行目标仓库。

按需用 `sand_read` 读仓库对象及其提交和索引信息；用本地 Git HEAD 及文件内容核对工具结果，记录 `read_source` 返回的 `reference`（路径、行范围和 hash）。不要把 `sand_status` 的白板修订号当成 Git 提交。若 Codex 尚未看到 `code_repo`，确认已启用代码包并导入仓库；若宿主没有刷新工具列表，重开会话再测，不用 shell 读取冒充 MCP。

## 第二段：共享关注范围与讲解

从「仓库」的搜索结果把一个源码引用添加到当前白板，另建一张带独特文字的便签（例如“请优先解释这个输入的去向”），选中它们。在同一 Codex 对话发出：

> 用 `sand_context` 读当前白板和选区，再用 `sand_read` 读便签正文。结合 `code_repo` 读到的源码，解释这条路径的用途、输入、输出和不确定点。用 `sand_types` 确认 `base.note` 的 schema，再用 `sand_edit` 把讲解作为一张新便签放在当前白板，附上对应文件和行号。不移动或改写原对象，也不改源码。

核对讲解便签确实出现、历史记录标识 Agent，且原布局与固定位置不变。人工抽查解释是否受到引用支持，匹配到源码摘录不代表解释正确。然后换一个选区，请 Codex 再调 `sand_context`，确认它报告新选区，不复述旧结果。

文字工具路径另外验证：

> 用 `sand_activity` 报告你正在关注讲解所引用的源码对象；再用 `sand_context` 核对人的选区。不要替我移动界面，也不要修改白板内容。

有独立浏览器时，对照活动提示以及操作前后的选区与视角；没有界面时，只记录文本工具的返回，界面观察标“未测”。Agent 活动自报是关注提示，不是操作者选区，也不是 UI 指令。

## 第三段：活动、变更与生命周期

要求 Agent 在实际读取前通过 `sand_activity` 报告任务（`state: "running"`，传入任务、动作、当前白板或对象），完成后报告 `done`。核对来源为自报，不称为系统监控；在没有新报告的情况下，`running` 活动 10 分钟后过期，`done` 2 分钟后过期。

在外部仓库的可丢弃副本中，由验收者手动改一处被引用文件但不提交。重新请求 `code_repo` 的 `read_source` 应报源码已变、需刷新，不应将旧摘录当成当前内容。用 `code_repo` 的 `refresh` 重新索引后再读取，核对 Git HEAD 未变但文件 hash 变化；原讲解仍对应旧证据，需重读才可更新。不把产品的源码只读当作宿主对文件写入的保证。

分别关闭浏览器、断开 Codex、停止并重启工作台。重启复用相同工作空间及会话路径，再从 Codex 读回验收便签与对象 ID，核对已保存作品没有丢失。复制或切换到其他工作空间不算恢复；未恢复的运行状态也不能从作品仍存在推断为正在执行。

## 第四段：新交互与明确改动

在可丢弃的外部仓库副本操作，先记录实际脏状态；不要在唯一工作副本试破坏性场景。

1. 在“组件”新增研究比较白板，双击进入；填入自己确实观察到的图表和比较。返回总览，复制同一源码引用，移动和缩放一个实例，确认另一个保持独立。添加含义明确的关系，固定位置后尝试移动。
2. 在“外观”切换纸张、黑白和自定义；实际 Mac 检查中文输入法、键盘焦点、放大阅读和减少动效。
3. 在“改动”填写一个小需求，检查允许文件列表，提交意图。要求 Agent 读取意图、实际文件和现有行为，再提交具体提案和验证计划。
4. 不确认先要求 Agent 停在等待；核对文件没有被写入。审阅完整 Diff，要求修改一个方案细节；旧版本确认不得复用。确认当前版本和摘要。
5. 人在白板确认当前提案后，直接在 Codex 请求继续：让 Agent 用 `code_change` 的 `prepare_apply` 和 `read_approved_file` 逐文件核对，再用宿主文件工具写入，最后用 `verify` 核对实际结果、用 `report_validation` 记录测试命令、环境和输出。观察板上是否区分 Agent 自报与实际文件核对。
6. 人工改一处范围外文件，再核对；应显示偏离。恢复后再次核对。在同一 HEAD 下改变目标内容，旧引用和旧报告不得继续当成当前证据。
7. 测试多文件只写一份时的部分应用、停止后重连、刷新后的提案状态。不要把已写文件“自动回滚”当成产品已有能力；恢复由宿主／Git 明确执行。

确认约束的强制性单列：仅工作约定、宿主实际拦截，还是未验证。app-only 不等于调用者认证，不能仅凭 UI 按钮证明宿主无法绕过。

## 初学者真人任务

找未参与开发、不能直接阅读该语言代码的人，在未读解答的外部项目开始。只给启动与接入说明，不逐步口头引导：

- 找到项目用途和一个入口，说明输入如何经过至少三个部分产生输出。
- 用源码依据解释一个关系，指出一个尚不能确认的点。
- 编排一组关注内容，要求 Agent 复述意图；检查它是否把白板误认为工作区或修改授权。
- 表达一个边缘小功能／Bug，审核提案范围和影响，完成验证并复述结果。
- 在非代码研究预设中建立一次实际数据比较。

记录成功时间、错误操作、求助次数、放弃位置、对依据和影响的复述。评审者核对解释是否有证据支持。不要用开发者代操作或脚本点击冒充真人通过。对照安排和盲评分见 [验收工具](../acceptance/README.md)。

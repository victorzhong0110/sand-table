# 内核 v3：决策

日期：2026-10-22。决策人：项目所有者授权架构负责人决定。
本目录（`docs/kernel-v3/`）是 v3 的唯一设计依据。与 `docs/DEVELOPMENT_PLAN.zh-CN.md`、`docs/architecture/`、`workbench/docs/` 冲突时，以本目录为准。

## 为什么要 v3

v2 能跑，但有六个结构问题，继续在上面加组件只会更难改：

1. `core/model.ts` 的 `Board` 是一个上帝对象：代码投影、两套关系（`spaceLinks` 和 `objectRelations`）、两套活动、代码改动流程（意图/提案/验证）、讲解和导览全挂在上面。内核声称不含领域语义（I19），实际含了。
2. 持久化是整份 `workspace.json` 重写。真实工作空间里 10 个对象就有 127KB，历史记录占 73%；审计日志从不裁剪；每停顿约 400ms 就整份重写一次。写小说这类长期作品撑不住。
3. 两个进程（本地服务、直接启动的 MCP 服务）各自在内存里持有一份白板，只能靠自写的跨进程文件锁防止互相覆盖。
4. 给 AI 的 MCP 工具有 50 多个，挤占上下文，模型容易选错。
5. 组件类型是两套写法：内置类型在 `core/spaces.ts` 里手写 `switch` 和校验，领域类型用 `fields` 加 `check` 函数；渲染器靠猜字段形状，出现了“年龄 0”、参与者字段和参与关系双写等问题（#33）。
6. 画布交互自己写，拖动闪烁、缩放手柄、删除键、快捷键等基础手感问题不断（#29、#30）。

## 决策

### K1 通用内核 + 包

内核只提供机制：对象、关系、白板、展示、历史、审计、附件、类型注册表、统一写入。所有内容类型都由“包”声明，包括便签和白板本身。

- `base` 基础包：通用类型（便签、标题、白板、媒体、链接、表格、图表……）。随内核发布，界面上不能停用。
- `novel` 小说包、`research` 科研包、`code` 代码包：可以启用或停用。
- 用户也可以导入自己的数据包（见 K9）。

### K2 存储：每个工作空间一个 SQLite 文件

- 用 Node 内置的 `node:sqlite`（项目要求 Node 22.18+，已内置，不需要原生依赖，`.mcpb` 打包不受影响）。
- 位置：`<根目录>/<工作空间 id>/workspace.db`，附件放同目录 `blobs/<sha256>`。
- **数据库是唯一权威。进程不持有权威的内存副本**：每次读都查库，每次写都是一个事务。多个进程同时打开同一个库是安全的（SQLite 负责加锁）。因此删除自写的文件锁 `core/workspace-lock.ts`、整份原子写和 `.bak` 回退。
- 被否决的方案：
  - 继续用 JSON 整份重写：写放大，无法支撑长期作品。
  - CRDT（Loro、Yjs）：单人本地使用不需要；概念复杂度超过当前开发能力。将来要做多人实时协作时再评估。
  - `better-sqlite3`：原生模块，打包麻烦。接口和 `node:sqlite` 几乎一致，作为备选，`kernel/db.ts` 封装一层以便替换。

### K3 唯一写入口

界面、MCP、包对作品内容的编辑都调用 `kernel` 的 `applyCommands(batch)`。一次调用 = 一个数据库事务 = 最多一条历史记录（同一个 `intentId` 的连续写入合并成一步）。全部成功或全部失败。新库导入、运行状态及工作空间管理的限定边界见 `01` V8 和 `05` §3；不得以“不进历史”为由绕过内容命令。

### K4 数据模型收敛

- 一切内容都是**对象**。
- **展示**必须绑定一个对象（取消 v2 的“本地内容”展示）。“再放一份”= 新展示指向同一对象；“独立副本”= 复制出新对象。
- **关系**只有一套，类型名来自注册表。
- **白板**是一种可以进入的对象（类型声明 `container` 能力）。工作空间有一块首页白板。
- 代码领域的数据（文件、符号、意图、提案、验证）变成代码包的对象类型；讲解和导览变成基础包的类型。
- 删除 v2 的 `Board` 上帝对象，以及 `Space`、`SpaceLink`、`ComponentInstance`、`Item`、`Projection`、`placements` 这些概念。术语表见 `01-data-model.md`。

### K5 类型契约：JSON Schema

- 每个类型用 JSON Schema 声明数据形状，用 Ajv 校验。界面提示放在 `x-sand-*` 扩展关键字里。
- 同一份 Schema 同时用于：写入校验、AI 读取（`sand_types` 原样返回）、界面自动生成卡片和编辑表单。
- “未设置”就是字段不存在。内容字段禁止写占位默认值（不再出现“年龄 0”）。
- 指向其他对象的语义一律用**关系槽**声明，不允许把对象 id 存在结构化数据字段里（消除字段和关系双写）。Markdown 正文可以含 `sand://object/<编码后的 id>` 导航链接；正文是其唯一权威，不同步持久关系、不代表参与/支持等语义事实。具体规则见 `05-delivery-contracts.md` §2。
- 细节见 `03-types-and-extensions.md`。

### K6 MCP 工具：模型可见的核心工具固定 8 个

- 模型可见：`sand_status`、`sand_types`、`sand_query`、`sand_read`、`sand_edit`、`sand_history`、`sand_context`、`sand_activity`。
- 每个启用的领域包最多再注册 2 个工具（如 `code_repo`、`code_change`、`research_pdf`）。
- 界面专用的操作（视角、选区、上传附件、管理工作空间、批准提案……）用 MCP Apps 的 `visibility: ["app"]` 注册，模型看不见。**批准 AI 提交的提案只能由人在界面上做**，所以它必须是界面专用工具。
- 新旧工具对照见 `02-commands-and-tools.md`。

### K7 画布：React Flow 做受控视图层

- 用 `@xyflow/react`（React Flow，MIT 许可）承担选择、拖动、缩放、框选、删除键、视口这些交互。
- 它是“受控”的：节点和连线由内核数据生成，拖动结束后通过 `applyCommands` 写回。数据权威仍在内核。
- 被否决的方案：
  - tldraw：自带文档存储，会和内核争夺数据权威；许可条款近年有变化，需要另外核查。
  - 继续自写：#29、#30 说明交互细节的成本太高。
- 细节见 `04-canvas.md`。

### K8 富文本与功能组件的技术选择

- 富文本的**存储格式是 Markdown**（GFM 加 `$公式$`）。AI 原生读写 Markdown，也便于搜索和比较。
- 编辑器在组件阶段做一次技术验证后选定，候选 TipTap、Milkdown，条件是对支持的子集能无损往返 Markdown。
- 公式用 KaTeX；PDF 继续用已有的 pdf.js；图表在组件阶段按包体积预算选定，默认候选 Vega-Lite。
- 这些都是组件阶段（#37–#42）的事，内核阶段不引入。

### K9 扩展分两级

- **一级：数据扩展**（v3 内核阶段就支持）。一个 JSON 清单，可以声明新类型（JSON Schema）、关系词表、模板、预设。不含代码，不能注册 MCP 工具。取代 v2 的组件包协议。
- **二级：代码扩展**（组件阶段之后）。自定义视图在沙箱 iframe 里运行，只能通过消息接口读写自己的对象。内置包的自定义视图现在就按同一套接口写，将来第三方视图直接复用。
- 只有内置包能注册 MCP 工具。

### K10 迁移：渐进替换

1. 在 `workbench/kernel/` 新建 v3 内核，有完整测试，不碰 v2 代码。
2. 写一次性导入器：打开工作空间时如果只有 `workspace.json`，就导入成 `workspace.db`。旧文件原样保留，不覆盖。v2 的撤销历史不迁移（形状不同），导入后提示用户。
3. 新工具面在环境变量 `SAND_KERNEL=v3` 下启用，界面逐步切换。
4. 全部切换并验收后，删除 v2 内核代码。

### K11 先能用，再重构

项目所有者现在一用就卡住。Phase 0 先修现有版本里阻塞使用的缺陷（#26、#28、#29、#30、#31），和内核开发并行。v2 里将被替换的代码，只修阻塞使用的问题（丢数据、无法继续操作），其余标 `v3-covered` 等新版本解决。

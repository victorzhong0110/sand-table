# Sand Table：产品定义、架构与开发规划

版本：0.1 · 设计基线  
日期：2026-10-18（Asia/Taipei）  
仓库：https://github.com/victorzhong0110/sand-table  
状态：产品方向与架构规划文档；本文中的目标能力尚未实现或验收。编写本文不代表启动功能开发。

## 1. 文档用途与决策状态

本文整理项目讨论结论，供后续设计、实现、代码审查和真人验收共同使用。核心原则是先确定用户需要理解和完成的事情，再选择技术与组件，避免现有代码反过来限定产品。

文档使用三种状态：

- **已确认方向**：用户明确提出或在讨论中认可的产品目标与交互原则。
- **规划方案**：为实现目标提出的架构、数据模型、工程拆分和阶段安排；具体实现可通过设计记录调整。
- **待决事项**：仍需要原型、源码评估或用户讨论才能确定的选择。

后续开发应维护本文的状态，不得把计划中的能力写成已经完成，也不得把一次示例演示视为真实仓库或初学者验收通过。

### 1.1 已确认方向

## 2. 产品目标

### 2.1 一句话定义

**Sand Table 让人从理解软件的行为出发，逐步深入架构与代码，与自己的 AI 一起完成有依据、可验证、可协作的改进。**

面向用户，可以描述为“人和 AI 的共同工作室”或“交互沙盘”；面向开发者，定义为“让人和 AI 共享上下文的空间交互框架”。

设计意象：像黑板一样容易修改，像绘本一样容易理解，像沙盘一样呈现整体关系。绘本指逐步揭示、图文配合和自然理解，不意味着儿童化视觉。

### 2.2 目标用户与起点

首要用户能够描述问题、比较方案、提出反例，但未必理解仓库目录、编程语言或开发工具链。

理想起点是：用户克隆一个 GitHub 仓库，选择自己的 Agent，打开 Sand Table，得到可以探索、追溯和持续维护的项目空间。

长期应支持活跃、规模较大的开源项目。用户提及的 Hugging Face 生态项目、DeepSeek harness 类项目是目标场景举例，不是首版已承诺支持的具体仓库清单；后续需要确定准确仓库、提交版本和验收任务。

辅助用户包括：接手陌生代码的开发者、维护者、教师，以及希望向别人解释实现的人。

### 2.3 “理解整个仓库”的可执行定义

不承诺首次打开就让用户理解全部代码。产品应提供：

1. 对项目用途、主要功能、架构边界和关键运行路径的可靠概览。
2. 从任何已支持的功能入口，逐步追踪相关实现、数据、依赖和验证依据。
3. 为暂未索引、无法解析、外部依赖和不确定关系提供清楚说明。
4. 允许用户围绕当前任务获得足够深入的理解，并随使用逐步拓展。

所有受支持代码应有检索和追溯入口；不要求每个代码块都常驻成一张卡。索引覆盖率、解释覆盖率和运行观测覆盖率分别报告，不能合成一个“理解百分比”。

### 2.4 成功时用户能够回答的问题

- 这个项目解决什么问题？主要部分如何合作？
- 用户做某个操作后，数据和控制经过哪里？
- AI 当前在做什么、为什么需要这些上下文、已经产出什么？
- 当前修改想改变什么，哪些行为应该保持？
- 解释、关系与结论的依据在哪里，哪些仍不确定？
- 哪个测试或运行结果验证了哪个版本？
- 现在需要我决定什么？这次改动怎样向维护者说明？

### 2.5 范围边界

首版目标是完成一个已有仓库中可复现、影响范围明确的 Bug 修复闭环，再进入需要更多设计取舍的新功能。

首版不承担完整 IDE、独立通用 Agent 执行平台、所有语言的完备静态分析、生产集群管理、多用户实时协作或完整仿真系统。可以通过现有编辑器、执行器与服务连接这些能力。

逻辑能力是进入产品的门槛；技术概念通过具体问题逐步学习。产品不声称任何人无需学习即可正确修改任意系统。

社区认可取决于贡献质量及维护者判断。框架应提高可理解性、验证质量和审查便利性，不把外部合并结果作为唯一产品验收条件。

## 3. 首个完整用户旅程

| 阶段 | 用户行为 | 系统应提供的帮助 | 可检查结果 |
|---|---|---|---|
| 打开项目 | 选择已克隆仓库和 Agent | 识别版本、语言、入口、文档，说明分析覆盖范围 | 项目身份与初始白板 |
| 建立理解 | 从一个用户功能进入 | 用途、输入输出、主要路径、术语说明、源码证据 | 用户能复述一条实际路径 |
| 界定问题 | 描述异常和期待 | 关联 Issue、复现步骤、预期与实际结果 | 可重现的问题与行为约定 |
| 讨论方案 | 圈选局部或使用直接动作 | 影响范围、候选方案、未知项与待决问题 | 用户能解释选择与取舍 |
| 指导实施 | 指派任务或启动已有 Agent | 清晰的任务范围、上下文、活动与变更记录 | 有版本身份的补丁和产出 |
| 检查结果 | 查看 Diff、测试和预览 | 连接需求、修改与验证；显示未覆盖风险 | 用户判断是否达到目标 |
| 社区贡献 | 准备并按用户意图提交 PR | 贡献规则、动机、复现、验证与审查反馈 | 可供维护者审查的贡献 |
| 回看与维护 | 回放过程、查看后续变更 | 阶段比较、版本关联、解释过期提示 | 可追溯的任务历史 |

发布 Issue、PR、评论或其他外部消息须依据明确用户意图或已有授权。生成草稿与实际发送是可区分的动作，不能因为 AI 分析完成就自动发布。

## 4. 内容与交互模型

### 4.1 核心概念

| 概念 | 定义 | 身份与职责 |
|---|---|---|
| 对象 Object | 被理解或操作的实体 | 独立身份、内容、状态和来源，例如功能、函数、任务、运行 |
| 组件实例 Component Instance | 对象或本地内容在某处的展示入口 | 位置、尺寸、展示配置、交互状态；可引用同一对象的不同视图 |
| 组件类型 Component Type | 一类组件的声明与实现 | 数据契约、渲染器、能力、可用动作、配置与迁移 |
| 白板 Board | 组织组件实例的空间 | 成员、布局规则、局部上下文；可作为组件嵌入其他白板 |
| 关系 Relation | 对象或组件之间有类型的联系 | 端点、方向、含义、证据、有效时间与确认状态 |
| 视图 View | 对共享内容的一种观察配置 | 摄像机、筛选、关系图层、展开状态、时间与展示选择 |
| 动作 Action | 用户或 AI 发起的意图 | 明确目标、输入、作用域、前置条件及副作用 |
| 变更 ChangeSet | 一组可审查的状态修改 | 基础版本、修改项、发起者、说明、应用结果与历史 |
| 事件 Event | 已记录的发生事实 | 发生时间、记录时间、来源、关联对象与因果信息 |
| 引用 Reference | 到对象、内容位置或版本的定位 | 逻辑身份与解析结果分开，支持有效、过期、缺失等状态 |

便签、标题等可以直接拥有本地内容，不要求用户先创建独立对象。内部模型仍需分清展示实例与外部实体。

### 4.2 对象复用与白板嵌套

同一服务可以在总览里显示状态点，在任务板里显示相关代码，在过程板里显示某次运行。对象数据共享，实例布局独立。

建议的规则：

- 每个组件实例属于一个白板；复用对象时创建新的展示实例。
- 删除展示实例不等于删除对象、文件或远端资源；删除语义必须明确。
- 白板的实际容纳结构不允许循环；跨白板引用可以形成一般关系图。
- 展示另一白板时区分嵌入与导航引用，防止递归渲染失控。
- 共同引用同一白板时，独立保存每个嵌入实例的查看状态；修改成员内容是否共享必须可见。
- 固定一个组件时，用户期望的空间位置不能因祖先重排而悄悄改变；自动布局必须识别这一约束。

白板支持区域、摘要、入口和局部预览几种呈现。缩放和展开改变信息深度，避免无止境的嵌套边框。

### 4.3 关系与空间语义

区分三层：

1. **编排关系**：为了阅读、比较或关注，把内容放在一起。
2. **明确领域关系**：调用、实现、依赖、验证、引用、归属等。
3. **推断关系**：人或 AI 提出的假设，尚未被来源充分支持。

靠近可以让 AI 推测用户想一起看，但不能自动建立代码依赖。将组件放入白板也不必然改变对象所属项目或部署环境。

关系不仅通过线表达，也可通过包含、对齐、区域、标签、共享高亮表达。箭头图层按需开启，支持追踪上游、下游和某条路径。显示“可能受影响”时，不得把静态连接直接当作已验证的运行影响。

### 4.4 多视图与规模

同一内容可拥有功能、架构、当前任务、运行和贡献视图。它们通过对象身份联动，不维护彼此独立的“事实副本”。

大图需要语义缩放、渐进加载、折叠、搜索定位、局部视窗、路径聚焦、面包屑与返回位置。总览同时覆盖主要领域，不要求同时渲染全部细节。

自动更新优先保持用户已熟悉的位置；避免新数据到达就重新排列全图。

## 5. 组件体系

### 5.1 基础组件、可组合能力、场景预设

采用三层组织：

- **基础组件**：文本、资源、图表、表格、状态、代码、容器等可复用展示与交互。
- **可组合能力**：时间、引用、详情、操作、AI 上下文、容纳、比较等。
- **场景预设**：由基础组件和能力组成的项目白板、Bug 修复白板、过程白板等。

预设不是写死的业务流程。用户可以增删组件、改编排、配置数据和请求 AI 调整。

### 5.2 通用组件目录

| 类别 | 组件 | 第一领域用途 |
|---|---|---|
| 容器 | 普通白板、分组区域、过程白板 | 项目、功能、任务和过程组织 |
| 说明 | 文本、标题、便签、批注 | 背景、疑问、约束和局部解释 |
| 资源 | 文件、文档、图片、音视频、链接卡 | 文档、截图、复现材料和输出 |
| 数据 | 指标、状态、图表、表格、事件流 | 检查状态、执行统计和运行变化 |
| 工作 | 任务、清单、Agent 活动、操作面板 | 任务拆解、执行和人工介入 |
| 推理 | 问题、证据、比较、方案、决策、行为约定 | 区分问题、证据、取舍和结论 |
| 导航 | 对象引用、白板入口、局部视窗 | 深入局部与跨视图定位 |

### 5.3 代码开发领域组件

| 组件 | 摘要 | 深入后展示或执行 | 关键关联 |
|---|---|---|---|
| 项目／仓库 | 用途、版本、工作区状态、覆盖范围 | 文档、入口、依赖与贡献说明 | 仓库身份、提交、工作区 |
| 功能／模块 | 用户用途、输入输出、状态 | 调用路径、实现、接口与测试 | 功能—实现—验证 |
| 代码引用 | 文件、符号、片段及说明 | 固定版本源码、编辑器定位 | 路径、符号、版本、内容摘要 |
| 需求／任务 | 目标、进展、阻塞 | 方案、约束、验收条件 | Issue、行为约定、变更 |
| 行为约定 | 现在与期望的行为 | 输入示例、反例、不变条件 | 复现、测试和预览 |
| Agent 活动 | 执行者、当前工作、等待原因 | 已公开的操作、上下文引用和产物 | 任务、会话、工具调用、补丁 |
| 变更／Diff | 修改范围、目的、状态 | 文件级与片段级比较、评论 | 基础版本、目标版本、任务 |
| 运行／测试 | 状态、结果、耗时 | 命令、环境、日志、失败定位 | 实际被测版本与运行身份 |
| 预览／成果 | 页面、截图、输出文件 | 交互预览、附件及反馈 | 构建、运行、对应版本 |
| Issue／讨论 | 问题、标签、讨论状态 | 复现、已有意见、相关变更 | 来源与同步时间 |
| PR／审查 | 分支、检查、待处理意见 | 修改说明、逐项反馈、更新 | 精确提交与检查结果 |
| 贡献约定 | 项目要求摘要 | 原始指南、模板、流程 | 规则来源、版本和用户确认 |

Agent 活动只展示执行器提供的操作记录、状态、简要说明和公开输出，不要求获取或生成模型的隐含思维链。没有可靠状态来源时显示未知或断开，而不是用动画伪装正在工作。

### 5.4 可组合能力与注册契约

组件类型应声明：

- 稳定类型标识、结构版本、配置 schema、默认尺寸和可用呈现层级。
- 支持的数据类型、详情渲染、时间响应、比较、容纳与导出能力。
- 可提供的动作及其前置条件。
- 对 AI 可读的语义摘要、配置说明、允许修改的字段。
- 无障碍名称、键盘操作和加载、空白、错误状态。
- 配置迁移与不支持版本时的降级展示。

自定义分为配置、组合、代码扩展。未知组件保留原始数据，显示可理解的占位与说明，不能在导入或保存时静默丢失。

## 6. Metadata、来源与外部链接

### 6.1 元数据分组

| 分组 | 建议字段含义 |
|---|---|
| 身份 | 对象／实例 ID、类型、结构版本、仓库或工作区身份 |
| 布局 | 所属白板、位置、尺寸、折叠、固定、布局约束 |
| 内容绑定 | 本地内容或数据引用、参数、缓存策略 |
| 来源 | 来源种类、原始位置、采集方式、采集者、版本 |
| 时间 | 发生时间、记录时间、有效区间、时间跟随方式 |
| 新鲜度 | 最后读取、过期条件、当前版本是否匹配 |
| 可信状态 | 已观察、文档陈述、推断、人工确认、存在冲突 |
| 能力 | 可展开、可比较、可编辑、可回放、可执行动作 |
| 协作 | 内容作者、发起 Agent、提案状态、修改范围 |
| 展示 | 摘要方式、主题覆盖、语义状态与无障碍标签 |

这些是逻辑分组，不意味着所有组件都要拥有所有字段。当前负载、任务进度、代码文本属于内容数据；来源、更新时间、版本和展示方式属于描述信息。

“人工确认”不保证事实永远正确；“AI 生成”不意味着必然错误。可信判断来自证据、版本和上下文，避免用一个不透明分数替代。

### 6.2 引用类型

- **来源引用**：解释或指标依据的文档、源码、API 或运行结果。
- **位置引用**：文件页码、代码符号、片段、日志区间。
- **对象引用**：另一个对象、白板或展示实例。
- **操作绑定**：由宿主注册的动作 ID、参数与执行条件。

代码定位建议保存仓库身份、提交或工作区修订、路径、符号信息、行区间及片段摘要。行号随编辑会变化，不能作为唯一长期身份。重命名和匹配失败必须显式报告，不能悄悄指向看似相似的代码。

操作绑定不是任意可执行脚本或隐藏在 URL 中的命令。链接解析、跳转和执行由宿主能力接口完成。

### 6.3 证据与过期

解释和关系可以引用多份证据，支持矛盾、失效与待核实状态。源码变化后，相关解释进入需要重新检查的状态；不要不加提示地沿用旧结论。

历史测试只能证明其实际执行的代码版本、配置和环境。工作区未提交变化应以独立工作区修订或内容标识关联，不可只记录分支名。

默认总览用短标签说明来源与新鲜度；展开后提供完整依据。演示数据与实际采集数据始终可区分。

## 7. 过程白板与时间模型

### 7.1 两种呈现共享同一过程

**时间游标模式**：拖动时间轴，在相对稳定的空间布局里查看当时对象、任务和执行状态。

**阶段展开模式**：将阶段或关键时刻铺开，比较输入、变化、结果与决策。阶段不必等长，也不必只有线性顺序；支持并行、分支、失败、重试和合并。

两种模式共享过程身份、对象引用、选中项、批注和来源。切换时保留阅读上下文。比较多个时刻可以使用显式比较实例，不改变对象的当前状态。

### 7.2 三种时间语义

| 模式 | 数据含义 | 显示要求 |
|---|---|---|
| 历史回放 | 已记录的事件与状态 | 显示版本、证据和记录缺口 |
| 计划编排 | 预期步骤、依赖与时间 | 明确标注计划，不当作已发生 |
| 演示推演 | 作者设定的情景或阶段 | 标注演示／模拟及假设 |

首个代码开发闭环优先实现有来源的历史回放与阶段比较；计划组件可展示意图，完整计划引擎和仿真引擎属于后续范围。

### 7.3 三条历史分开存储

1. 工作事件：Agent 操作、运行、测试、审查等发生记录。
2. 对象版本：文件、解释、任务内容、关系等版本。
3. 白板变更：移动、分组、批注、布局调整等编辑记录。

通过关联 ID、时间和版本连接，不能只把聊天记录或每次 Git 提交当成完整过程。

建议用事件与检查点重建可用状态，具体存储技术后定。区分发生时间和接收时间，处理延迟、重复与乱序事件。因果顺序优先依赖来源序号或显式关联，不能只凭不同机器的时钟猜测。

### 7.4 回放规则

- 回放不执行当时的动作，也不会自动回滚文件或远端资源。
- “查看当时状态”“恢复白板版本”“恢复代码版本”是不同动作。
- 无历史数据时显示缺口，不把当前值冒充历史值，不补造平滑变化。
- 嵌套过程白板默认跟随父白板时间；固定独立时间时提供可见标记。
- 用户回看时可提示新的实时事件，但不抢夺时间游标。
- 回看旧布局与用当前布局查看旧数据分别标注，避免误解。
- 对旧版本提出修改应形成基于当前状态重新检查的提案，不直接作用于当前工作区。

## 8. 交互与视觉原则

### 8.1 工具箱

| 模式 | 主要行为 |
|---|---|
| 浏览 | 选择、悬停、聚焦、展开、跳转、查看关系 |
| 编排 | 拖动、缩放组件、分组、调整位置与明确关系、固定 |
| AI | 圈定范围、提问、生成解释或方案、预览并应用修改 |

“解释、比较、定位、测试”等直接动作与自然语言使用相同的命令模型和目标对象。不同模式应有清楚反馈；浏览时避免误拖，拖动和调整大小不触发业务执行。

### 8.2 详情与渐进理解

远看展示用途、状态、异常和关键活动；展开后展示输入输出、来源、历史、解释与动作。关系路径和详情面板可以临时浮现，不永久增加图上噪声。

支持“先讲用途”“举一个输入输出例子”“解释术语”“深入到实现”。解释围绕当前任务，既不假定用户会编程，也不把复杂行为简化成错误结论。

悬停不能是唯一信息入口，键盘聚焦和点击应能获取等价信息。保留返回位置、阅读历史和局部锚点，避免用户在大图中迷路。

### 8.3 主题

- 黑白主题：简洁、清晰、对比和留白，参考用户提出的 Apple／OpenAI 风格方向。
- 纸张主题：温暖纸色、柔和表面层级、适合长时间阅读，参考用户提出的 Anthropic／Claude 风格方向。
- 自定义主题：颜色、字体、密度、圆角、动效等配置；不改变组件语义和动作行为。

主题通过共享设计令牌作用于所有组件。状态同时使用文字或图形，不只靠颜色。高密度图优先可读性，运行提示只在有状态依据时出现；支持减少动效、足够对比度和键盘导航。

## 9. 架构规划

本节为规划方案。模块边界优先于具体包名和存储选型；保持通用核心可以脱离 GitHub、Research OS 或某个 Agent 独立使用。

### 9.1 分层与依赖方向

~~~mermaid
flowchart TD
    A["宿主工作台／嵌入应用"] --> B["空间交互与组件渲染"]
    A --> C["代码开发领域包"]
    B --> D["通用模型与变更引擎"]
    C --> D
    A --> E["连接与能力适配"]
    E --> F["源码／Git／Agent／运行／GitHub"]
~~~

| 层 | 职责 | 不应承担 |
|---|---|---|
| 通用核心 | 对象、白板、关系、视图、引用、事件、变更与校验 | GitHub 字段、具体模型 API、Research OS 业务 |
| 交互层 | 画布、选择、布局、语义缩放、工具箱、详情、时间视图 | 擅自执行命令、直接决定领域事实 |
| 组件 SDK | 类型注册、能力声明、渲染、配置、迁移、降级 | 绕过宿主访问任意文件或网络 |
| 领域包 | 功能、代码、任务、测试、PR 等对象与预设 | 重新实现通用画布和历史机制 |
| 适配层 | 读取来源、解析引用、提交被允许的动作、接收事件 | 把无法获取的状态伪装为成功 |
| 宿主应用 | 会话、工作区、连接配置、持久化与用户授权 | 将宿主策略硬编码到通用核心 |

通用核心建议使用不依赖 UI 框架的数据与命令接口；首个 UI 实现可以沿用现有 TypeScript／React 技术基础。具体画布引擎、组件库和本地服务语言仍待评估。

### 9.2 建议模块划分

| 建议模块 | 主要内容 |
|---|---|
| core | 类型与 schema、引用、关系、变更校验、版本冲突 |
| canvas | 视口、选择、布局、导航、渲染调度 |
| components | 通用组件、注册机制、主题和详情面板 |
| timeline | 时间上下文、回放查询、阶段比较 |
| agent-bridge | 上下文封装、提案、执行状态协议 |
| domain-code | 代码开发对象、关系、组件和模板 |
| adapters | 本地仓库、编辑器、Git、执行器、GitHub 等连接 |
| workbench | 默认宿主与完整用户旅程 |
| examples | 最小嵌入应用和后续跨领域验证 |
| docs | 产品规范、架构决策、接口、验收、迁移与来源 |

这些名称不要求第一天就成为多个独立发布包。先维护清楚的依赖边界，避免为模块化增加过早的发布和构建负担。

### 9.3 逻辑数据契约

以下是接口讨论基线，不是已经冻结的 schema。

| 记录 | 最小信息 | 约束 |
|---|---|---|
| ObjectRecord | id、type、revision、content／binding、provenance | 与展示实例分离 |
| ComponentInstance | id、type、objectRef／localContent、boardId、layout、config | 不把坐标写回业务身份 |
| BoardRecord | id、成员、上下文策略、布局约束 | 容纳关系无循环 |
| RelationRecord | id、端点、type、assertion、evidence、validity | 推断与已支持关系可区分 |
| ViewState | board、camera、filters、expanded、selection、time | 可恢复，不改写外部事实 |
| SourceRef | 来源身份、版本、定位信息、内容摘要 | 可检测失效与错配 |
| ChangeSet | id、baseRevision、scope、operations、actor、reason | 校验后原子应用或明确失败 |
| ActionRequest | id、actionId、target、args、preconditions、authorityRef | 业务副作用由宿主实施 |
| ProcessEvent | id、processId、source、eventTime、recordedAt、关联版本 | 去重、乱序和缺失处理 |

持久化记录不存放访问凭据。数据 schema 与组件配置均需要版本字段；导入时执行迁移和引用检查，失败保留原始输入与诊断。

### 9.4 权威来源与投影视图

源码、Git、运行记录、GitHub、用户白板分别拥有自己的权威范围：

- Git 和工作区决定真实代码版本。
- 执行器提供命令与运行状态；请求取消不证明进程已经停止。
- GitHub 提供 PR、Issue 和远端检查的状态。
- 用户与 AI 在 Sand Table 中维护编排、批注、解释、方案和引用。
- AI 生成的解释是带来源的投影，不能覆盖真实来源。

源变更通知触发失效检查和局部更新。连接中断时允许查看缓存，但显式标出读取时间、断开状态和不可用动作。

### 9.5 持久化与恢复

规划采用“宿主提供存储接口，示例工作台优先本地保存”的方向；具体数据库和同步方案待决。

持久化至少涵盖：对象引用、组件与白板、关系、用户布局、提案、事件关联、历史检查点、组件版本和连接描述。浏览器存储可用于原型缓存，不应成为实际长期工作区的唯一副本。

导出包应包含 schema 版本、白板和引用清单、必要历史及外部材料的可用性说明；默认排除凭据，不隐含打包整个私有仓库。缺失的大文件、日志或外部资源在恢复时可识别。

备份／恢复验收需要检查布局、批注、提案和时间轴是否都恢复，不能只验证当前画面。多人实时协作可后置，但工作区修订和冲突检测应从首版具备。

## 10. 仓库理解与持续维护

### 10.1 建议分析流程

~~~mermaid
flowchart TD
    A["仓库身份与版本快照"] --> B["文件／符号／文档索引"]
    B --> C["候选功能与结构关系"]
    C --> D["证据关联与不确定性检查"]
    D --> E["项目白板与解释"]
    E --> F["用户修订与按需深入"]
    F --> D
~~~

具体职责：

1. 识别仓库、分支、提交、未提交变化、子模块和可用材料。
2. 索引文档、配置、入口和受支持语言的符号；排除生成物与大体积无关内容时记录原因。
3. 通过确定性分析获取可证明的结构事实，再用 AI 提出功能组织与解释。
4. 将关系与原始证据关联，并标出动态调用、反射、插件、配置驱动行为等静态分析盲区。
5. 按用户问题按需深入，不把全部源码一次性塞进上下文。
6. 需要运行证据时提出可检查的采集动作，由已有执行环境实际运行。
7. 源码变化后增量刷新相关对象与解释，同时保留人工组织和批注。

静态依赖图不等于实际调用轨迹；一次运行轨迹也不等于全部可能路径。两类数据在界面和模型中分别标明。

### 10.2 人工编排与 AI 维护

默认策略：

- 状态与来源数据可自动刷新，保持时间和版本可见。
- AI 可以提出新的解释、组件与关系，并在允许的局部自动维护摘要。
- 用户固定的位置、手动分组和阅读区域受到保护。
- 大范围重排、删除与语义关系改变以差异方案呈现。
- 用户可对某个区域开启更主动的整理，并随时收回。
- 用户编排作为偏好和意图线索保存，不自动升级为业务事实。

更新应说明新增、失效、冲突和需要确认的内容。用户应能选择局部接受，不必在“全盘接受”和“全部拒绝”之间二选一；拆分接受时仍需验证依赖与原子性。

### 10.3 解释质量

每份重要解释记录适用版本、证据引用和未确定问题。需要支持输入输出示例、反例、失败路径、术语解释以及“我哪里还没看懂”的继续探索。

不以 AI 自评代替质量检查。真实验收应检查关键路径是否遗漏、链接是否准确、用户能否用自己的话解释，以及面对反例能否识别解释的边界。

## 11. Agent 协作与动作模型

### 11.1 接入已有 Agent

框架不绑定模型供应商。Agent 适配器声明实际能力，例如：只读解释、提案生成、读取工作区、代码修改、执行命令、接收事件或取消请求。

首个适配器需要在实现前确定，不承诺同时完整接入所有工具。无 Agent 连接时仍可浏览、整理、导出上下文；有状态连接才展示真实活动。

### 11.2 统一上下文

直接按钮与对话共同生成结构化上下文，包含：

- 用户意图、选中对象与区域，以及显式任务目标。
- 当前工作区、源版本、白板版本、时间位置。
- 相关关系、证据、批注、行为约定与待决事项。
- 允许修改范围、固定组件、可用动作与执行器能力。
- 已截断或未读取的材料，以及上下文预算信息。

上下文不是整张白板的截图，也不是全部仓库内容的无差别复制。用户可以检查 AI 实际收到的范围，AI 可以请求额外材料。历史视图上下文必须带历史身份。

### 11.3 提案与应用

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant W as 白板宿主
    participant A as Agent 适配器
    participant X as 执行环境
    U->>W: 直接动作或自然语言意图
    W->>A: 版本化上下文与作用域
    A-->>W: 解释或变更提案
    W-->>U: 来源、差异与预期影响
    U->>W: 接受、调整或拒绝
    W->>W: 检查当前版本与约束
    W->>X: 执行已授权的领域动作
    X-->>W: 实际状态、版本与结果
~~~

纯解释可以直接呈现；显示信息不必引入多余确认。布局与内容修改根据用户已设策略应用；有外部副作用的动作遵循宿主现有授权。上述序列是需要审查时的路径，不要求每个低影响动作都弹出确认。

提案要携带基础版本和作用域。应用前检查版本冲突、引用、容纳循环、固定布局和允许字段。过期提案不能静默覆盖新状态；可解释冲突、重新生成或提供可审查的合并。

### 11.4 状态与失败

建议区分提案状态与执行状态：

- 提案：草稿、待审查、已接受、已拒绝、已失效、已应用。
- 执行：排队、运行、等待用户、成功、失败、取消请求中、已取消、未知／断开。

对于网络重试、重复回调与进程恢复，使用关联 ID 和幂等策略。不能因为 UI 请求返回就判定业务成功。恢复连接后以执行器的实际状态协调，不自动重复具有副作用的操作。

布局撤销可在白板内完成；文件、进程、PR 等外部动作的恢复由适配器提供，不能承诺所有操作都能撤销。

### 11.5 访问边界

仓库文件、Issue 文本、日志和外部链接都是被分析的数据，不能自行扩大执行权限。组件导入与扩展安装不自动获得宿主文件系统、命令执行和凭据访问权。

运行项目、安装依赖、发送数据到模型、提交远端变更分别对应具体能力与用户意图。界面应把必要的信息放在相关动作处，不用一套泛化弹窗阻碍正常阅读。

## 13. 分阶段开发规划

按可验收成果推进，不在尚未明确人员与范围时承诺日期。阶段可以迭代，但不得用后续愿景掩盖当前缺口。

### P0：设计基线与可行性检查

**目标**：把关键决策转成可评估的方案。

交付：

- 本文、核心使用故事、决策记录和组件清单。
- 现有代码及参考项目的模块盘点与来源记录。
- 普通白板、过程白板双模式、任务闭环的交互线框或低成本原型。
- 候选画布引擎、首个 Agent 适配器、源码索引范围、持久化方案的决策记录。
- 一个固定版本、可复现问题的验收仓库；确认任务及复现环境。

通过条件：主要概念能覆盖示例；用户能够理解交互故事；技术选择有证据；已得到开始功能开发的明确指令。

### P1：独立空间交互骨架

**目标**：在无 Research OS 后端依赖的情况下，完成可保存、可恢复的白板体验。

交付：

- 核心模型与组件注册机制。
- 白板嵌套、对象多实例、选择、拖动、尺寸、分组、固定、关系、搜索和详情。
- 浏览／编排／AI 入口；AI 暂可使用明确标注的协议模拟。
- 黑白、纸张和基本自定义主题。
- 导入导出、持久化、撤销与版本冲突处理。
- 最小嵌入示例，证明核心与宿主分离。

通过条件：用户编排在重载后保留；未知组件不会丢失；固定约束有效；可键盘操作主要流程。模拟数据和模拟 Agent 明确可见，不宣称真实仓库理解。

### P2：基于证据的仓库理解

**目标**：用户可以从一个真实功能追踪到实现。

交付：

- 本地仓库身份与版本、索引覆盖报告、文件／符号引用。
- 功能与模块地图、关键路径、证据详情和术语解释。
- 真实 Agent 只读解释能力，带来源和不确定性。
- 源变更检测、解释过期和局部刷新。
- 原始代码与编辑器跳转。

通过条件：固定仓库的关键路径与人工核对结果一致；每个关键断言可追溯；未知部分可见；初学者能复述功能路径。首批语言与解析范围明确列出，不泛称支持任意仓库。

### P3：指导 AI 的修改与验证闭环

**目标**：完成一个真实、可复现 Bug 的局部修改。

交付：

- 任务、行为约定、方案、决策、Agent 活动、Diff、运行／测试与预览组件。
- 统一直接动作和对话上下文。
- 变更提案、作用域与过期检测。
- 通过选定适配器接入实际代码修改、执行和结果。
- 失败、等待、断开、取消和恢复路径。

通过条件：用户可以指出原始失败、说明修改理由、检查实际被测版本及未覆盖内容；执行失败或未知状态不被显示为成功。

### P4：过程白板与长期可追溯

**目标**：工作能够在两种时间视图中被回看和比较。

交付：

- P1 起记录的白板变更和 P3 起记录的工作事件与对象版本的统一查询。
- 时间游标、阶段展开、分支／重试表示、阶段比较。
- 嵌套时间跟随、缺失历史标记、实时与历史切换。
- 检查点、恢复与过程导出。

通过条件：两种视图指向一致的对象与事件；回放没有执行副作用；历史缺口可见；备份恢复后过程仍可追溯。

时间契约在 P1 定义、在 P3 采集，不能等 P4 再尝试从聊天记录补造过去。

### P5：社区贡献闭环与首版验收

**目标**：用户能够形成可审查的贡献并理解反馈。

交付：

- 贡献指南、Issue、PR、检查与审查反馈连接。
- 有来源的 PR 草稿和提交前预览。
- 反馈映射到对象、代码、任务及后续修改。
- 初学者真人验收、真实仓库运行验收和问题修复。
- 面向用户的 README、安装指南、示例、限制及恢复说明。

通过条件：用户独立完成从理解到贡献材料的闭环；实际发布有明确授权；维护者的合并决定不作为功能通过的必要条件。首个真实 Bug 场景通过后，增加一个范围有限的新功能场景。

### P6：规模与跨领域扩展

**目标**：验证框架可扩展性。

交付方向：

- 更大仓库、多语言、更多 Agent 与开发环境适配。
- 增量索引、视口虚拟化、上下文成本与性能优化。
- 用户组件开发工具和可复用模板。
- 研究实验、基础设施运维、教学／知识、创作等领域包。

先用至少一个非代码场景检查核心是否夹带 Git、函数或 PR 假设，再扩大领域数量。未来的服务器负载、可用性、资源分配和服务状态组件属于领域扩展，不应反向占据通用核心。

## 14. 验收与测试策略

### 14.1 四类证据分别保留

| 类别 | 证明什么 | 不能替代什么 |
|---|---|---|
| 模型与接口测试 | 关系、版本、作用域和历史约束正确 | 用户是否能理解 |
| 浏览器交互验证 | 操作、恢复、主题和详情可用 | 真实数据与执行真实性 |
| 固定仓库集成验证 | 引用、分析、修改和运行链路实际成立 | 未测试仓库的普遍正确性 |
| 初学者真人验收 | 用户能独立理解、判断和推进任务 | 所有代码语义已被证明 |

测试围绕具体风险，不把截图数量或测试通过率作为产品价值的替代指标。界面和交互方式发生根本变化后，旧人工验收记录只能说明旧版本。

### 14.2 关键正确性检查

- 白板无容纳循环，同对象多实例保持数据一致。
- 删除展示不会删除实际资源；错误引用不会静默重定向。
- 固定组件、作用域和基础版本校验能够阻止越界或过期覆盖。
- 依赖关系、证据关系和编排关系不会混淆。
- 测试、预览和解释绑定正确源码版本。
- 重复事件、断线和恢复不会造成重复执行。
- 历史回放不执行动作；缺少历史时不会展示伪造状态。
- 导入导出和备份恢复保留自定义组件数据与必要历史。
- 中文输入法、键盘操作、焦点和减少动效能够正常工作。
- 实际 Agent 状态与动画显示一致；模拟／缓存／当前数据可区分。

### 14.3 真人验收任务

建议首轮至少邀请两位未参与实现、缺少相关仓库经验的用户；人数是形成早期反馈的规划下限，不代表统计性证明。

用户在固定构建与固定仓库版本上：

1. 说明项目用途和一个真实功能的输入输出。
2. 追踪该功能的关键路径，并指出至少一处来源。
3. 识别一条 AI 推断或证据不足的解释。
4. 描述一个复现问题，建立期望行为和不变条件。
5. 指导 AI 实施局部修改，说明主要影响。
6. 通过 Diff、测试和预览判断结果，指出尚未验证之处。
7. 在两种时间模式间切换，找到失败、调整和最终结果。
8. 准备 PR 说明并处理一条审查反馈；发布另按授权执行。
9. 重载或恢复工作区，找回编排与任务历史。

记录完成情况、理解错误、人工帮助、用时、迷失位置、对 AI 错误结论的识别情况。主持人代写命令或解释架构属于辅助，不能计为独立完成。

### 14.4 性能与规模

P0/P1 需确定可重复的性能场景：目标设备、仓库规模、可见／总组件数量、边数量、历史事件数量及展开深度。分别测量首次可交互、平移缩放、搜索、详情加载、时间拖动、索引更新和内存。

具体数字目标在原型测量后冻结，避免在无依据时承诺“无限画布”性能。大型仓库使用局部加载、索引缓存和可见范围渲染，不能要求一次性加载所有源码与所有组件。

### 14.5 阶段完成规则

每阶段记录实现提交、支持范围、测试与真人证据、已知缺口和下一步。功能可见、实现合并、自动检查通过、真人验收通过、社区 PR 被接受分别记录，不互相替代。

## 15. 待决事项与决策顺序

| 事项 | 当前倾向 | 最晚决策点 |
|---|---|---|
| 默认宿主形态 | 浏览器工作台配本地能力桥接；是否桌面封装未定 | P0 |
| 画布渲染与布局引擎 | 先比较已有实现与候选库，用嵌套、语义缩放和大图验证 | P0 |
| 首个 Agent 适配器 | 接用户已有工具，保持协议独立 | P0 |
| 首个验收仓库与任务 | 可复现、范围明确、固定提交的真实 Bug | P0 |
| 首批语言与代码分析能力 | 按验收仓库选定，明确不支持部分 | P0/P2 |
| 持久化与备份格式 | 宿主存储接口，本地优先，版本化导出 | P1 前 |
| 自动维护默认策略 | 自动刷新数据，保护人工编排，局部授权主动整理 | P1 |
| 是否内嵌完整代码编辑 | 首期以阅读、Diff 和编辑器跳转为主 | P2 前 |
| GitHub 接入方式 | 根据宿主与用户已有认证选取，避免重复凭据体系 | P5 前 |
| 扩展组件执行环境 | 声明式配置优先；代码扩展需隔离与能力声明 | 开放扩展前 |
| 多人协作 | 首版单人加自己的 Agent；保留版本和冲突机制 | 后续 |
| 计划与仿真深度 | 先展示计划并与历史区分，完整引擎后置 | P4 后 |

不要求用户一次回答所有工程问题。可用原型和证据解决的选择，由后续实现者给出具体比较；涉及产品交互和能力边界的变化再与用户讨论。

## 16. 后续开发约定

- 从用户旅程和验收条件拆分 Issue，每项关联本文的具体目标。
- 对对象身份、历史、动作权限、插件边界等重大改变建立架构决策记录。
- 每个实现 PR 说明解决的问题、行为变化、验证方式和实际限制。
- 示例数据和真实连接分别标识，不将演示能力写入已支持清单。
- 组件、领域包与宿主之间的依赖方向由代码审查和必要自动检查维护。
- 引入第三方代码时固定来源与许可，验证适配范围，不直接继承外部项目全部规则。
- 原 README 的旧运行方式在替换实现前保留说明；新能力就绪后再更新面向用户的入口。
- 任何设计调整都应保留这里最重要的目标：让用户形成自己的理解与判断，并能据此指导 AI。

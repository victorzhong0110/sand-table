## 1. 文档用途与决策状态

本文整理项目讨论结论，供后续设计、实现、代码审查和真人验收共同使用。核心原则是先确定用户需要理解和完成的事情，再选择技术与组件，避免现有代码反过来限定产品。

文档使用三种状态：

- **已确认方向**：用户明确提出或在讨论中认可的产品目标与交互原则。
- **规划方案**：为实现目标提出的架构、数据模型、工程拆分和阶段安排；具体实现可通过设计记录调整。
- **待决事项**：仍需要原型、源码评估或用户讨论才能确定的选择。

后续开发应维护本文的状态，不得把计划中的能力写成已经完成，也不得把一次示例演示视为真实仓库或初学者验收通过。

## 2. 产品目标

### 2.1 一句话定义

**Sand Table 让人从理解软件的行为出发，逐步深入架构与代码，与自己的 AI 一起完成有依据、可验证的改进。**

面向用户，可以描述为“人和 AI 的共同工作室”或“交互沙盘”。长期目标是让这种交互方式取代以对话框为主的 AI 使用方式，并成为人和 AI 共享上下文的空间交互框架；首版只交付工作台（D01），板子位于用户已订阅的 AI 对话之中（D15）。

设计意象：像黑板一样容易修改，像绘本一样容易理解，像沙盘一样呈现整体关系。绘本指逐步揭示、图文配合和自然理解，不意味着儿童化视觉。

### 2.2 目标用户与起点

首要用户能够描述问题、比较方案、提出反例，但未必理解仓库目录、编程语言或开发工具链。

理想起点是：用户在自己已订阅的 AI 客户端（Cursor、Claude、ChatGPT、Copilot 等）里安装 Sand Table 插件，打开一个已克隆的仓库，请自己的 Agent 打开板子，得到可以探索、追溯并据此指导修改的项目空间。

长期应支持活跃、规模较大的开源项目。用户提及的 Hugging Face 生态项目、DeepSeek harness 类项目是目标场景举例，不是首版已承诺支持的具体仓库清单。验收仓库、提交版本和任务按 D19 从外部仓库选定。

辅助用户包括：接手陌生代码的开发者、维护者、教师，以及希望向别人解释实现的人。

### 2.3 “理解整个仓库”的可执行定义

不承诺首次打开就让用户理解全部代码。产品应提供：

1. 对项目用途、主要功能、架构边界和关键运行路径的可靠概览。
2. 从任何已支持的功能入口，逐步追踪相关实现、数据、依赖和验证依据。
3. 为暂未索引、无法解析、外部依赖和不确定关系提供清楚说明。
4. 允许用户围绕当前任务获得足够深入的理解。

所有受支持代码应有检索和追溯入口；不要求每个代码块都常驻成一张卡。索引覆盖率、解释覆盖率和运行观测覆盖率分别报告，不能合成一个“理解百分比”。

### 2.4 成功时用户能够回答的问题

- 这个项目解决什么问题？主要部分如何合作？
- 用户做某个操作后，数据和控制经过哪里？
- AI 当前在做什么、为什么需要这些上下文、已经产出什么？
- 当前修改想改变什么，哪些行为应该保持？
- Agent 在哪份实际工作区中工作，它当前活动对应总览中的哪些对象？
- 解释、关系与结论的依据在哪里，哪些仍不确定？
- 哪个测试或运行结果验证了哪份实际工作区内容，是否包含未提交变化？
- 现在需要我决定什么？这次改动怎样向维护者说明？

### 2.5 范围边界

首版目标是在外部仓库中完成一个可复现、影响范围明确的 Bug 修复闭环，再进入需要更多设计取舍的新功能。

首版不承担：完整 IDE、自有 Agent 运行时、所有语言的完备静态分析、持久化存储与历史回放、对外提交 Issue 或 PR、对外组件 SDK、生产集群管理、多用户实时协作或完整仿真系统。可以通过用户已有的 AI 客户端、编辑器与服务连接这些能力。

逻辑能力是进入产品的门槛；技术概念通过具体问题逐步学习。产品不声称任何人无需学习即可正确修改任意系统。

贡献质量通过不公开的外部基准与评分者盲评评估（14.3），不以外部合并结果作为产品验收条件。

## 3. 首个完整用户旅程

| 阶段 | 用户行为 | 系统应提供的帮助 | 可检查结果 |
|---|---|---|---|
| 打开项目 | 在已订阅的 AI 客户端里请 Agent 打开板子 | 识别仓库、当前 git 版本、语言、入口、文档，说明分析覆盖范围 | 项目身份与初始板子 |
| 建立理解 | 从一个用户功能进入 | 用途、输入输出、主要路径、术语说明、源码证据 | 用户能复述一条实际路径 |
| 界定问题 | 描述异常和期待 | 关联 Issue、复现步骤、预期与实际结果 | 可重现的问题与行为约定 |
| 讨论方案 | 圈选局部、指着对象提问 | 影响范围、候选方案、未知项与待决问题 | 用户能解释选择与取舍 |
| 表达意图 | 拖拽、分组、改字，并附文字说明 | 汇总为意图 diff，供 Agent 读取 | Agent 复述的意图与用户想法一致 |
| 确认目标版本 | 查看 AI 整理的目标版本 | 连接意图、修改范围与预期影响 | 用户接受、调整或拒绝 |
| 检查结果 | 查看 Diff、测试和更新后的板子 | 连接需求、修改与验证；显示未覆盖风险；绑定 git 版本 | 用户判断是否达到目标 |
| 回看 | 查看已记录的修改结果 | 已提交内容通过 git 历史定位；未提交修改显示当前差异与可用内容标识 | 明确哪些结果已有持久版本、哪些仍是工作区状态 |

对外提交 Issue 或 PR 不在首版旅程中（D13、D18）。生成草稿与实际发送是可区分的动作，不能因为 AI 分析完成就自动发布。

## 4. 内容与交互模型

### 4.1 核心概念

| 概念 | 定义 | 身份与职责 |
|---|---|---|
| 对象 Object | 被理解或操作的实体 | 独立身份、内容、状态和来源，例如功能、函数、任务、运行 |
| 组件实例 Component Instance | 对象或本地内容在某处的展示入口 | 位置、尺寸、展示配置、交互状态；可引用同一对象的不同视图 |
| 组件类型 Component Type | 一类组件的声明与实现 | 数据契约、渲染器、能力、可用动作与配置 |
| 白板 Board | 组织组件实例的空间 | 成员、布局规则、局部上下文；可作为组件嵌入其他白板 |
| 关系 Relation | 对象或组件之间有类型的联系 | 端点、方向、含义、证据与确认状态 |
| 视图 View | 对共享内容的一种观察配置 | 摄像机、筛选、关系图层、展开状态与展示选择 |
| 动作 Action | 用户或 AI 发起的直接动作 | 例如解释、比较、定位；明确目标、输入与作用域 |
| 意图 diff Intent Diff | 人在板子上的一串混合表述汇总 | 拖拽、分组、改字与文字说明；交给 AI 理解，不直接改文件 |
| 目标版本 Target Version | AI 根据意图整理出的具体修改提案 | 提案 ID／修订、工作区内容基线、具体补丁或目标内容、作用域与说明；确认绑定其内容 |
| 引用 Reference | 到对象、内容位置或版本的定位 | 逻辑身份与解析结果分开，支持有效、过期、缺失等状态 |

便签、标题等可以直接拥有本地内容，不要求用户先创建独立对象。内部模型仍需分清展示实例与外部实体。以上记录只存在于白板会话的内存中（D16、D27）；需要长期保留的文件由宿主或用户纳入 git 等已有记录机制。未提交写入不会自动进入 Git 历史。

### 4.2 对象复用与白板嵌套

同一服务可以在总览里显示状态点，在任务板里显示相关代码，在另一个视图里显示某次运行。对象数据共享，实例布局独立。

建议的规则：

- 每个组件实例属于一个白板；复用对象时创建新的展示实例。
- 删除展示实例不等于删除对象、文件或远端资源；删除语义必须明确。
- 白板的实际容纳结构不允许循环；跨白板引用可以形成一般关系图。
- 展示另一白板时区分嵌入与导航引用，防止递归渲染失控。
- 共同引用同一白板时，独立维护每个嵌入实例的查看状态；修改成员内容是否共享必须可见。
- 固定一个组件时，用户期望的空间位置不能因祖先重排而悄悄改变；自动布局必须识别这一约束。

白板支持区域、摘要、入口和局部预览几种呈现。缩放和展开改变信息深度，避免无止境的嵌套边框。

### 4.3 关系与空间语义

区分三层：

1. **编排关系**：为了阅读、比较或关注，把内容放在一起。
2. **明确领域关系**：调用、实现、依赖、验证、引用、归属等。
3. **推断关系**：人或 AI 提出的假设，尚未被来源充分支持。

靠近可以让 AI 推测用户想一起看，但不能自动建立代码依赖。将组件放入白板也不必然改变对象所属项目或部署环境。

在 D17、D28 下，动作区分为“整理”和“改动意图”。整理只调整本次会话的观看方式，可进入 AI 的背景上下文；不得被当成改代码的指令。改动意图经显式标记或文字说明后进入意图 diff。用户可以把一次整理转为改动意图；含义仍有歧义时，AI 先复述确认。

关系不仅通过线表达，也可通过包含、对齐、区域、标签、共享高亮表达。箭头图层按需开启，支持追踪上游、下游和某条路径。显示“可能受影响”时，不得把静态连接直接当作已验证的运行影响。

### 4.4 多视图与规模

同一内容可拥有功能、架构、当前任务和运行视图。它们通过对象身份联动，不维护彼此独立的“事实副本”。

大图需要语义缩放、渐进加载、折叠、搜索定位、局部视窗、路径聚焦、面包屑与返回位置。总览同时覆盖主要领域，不要求同时渲染全部细节。

本次会话中，自动更新优先保持用户已熟悉的位置；避免新数据到达就重新排列全图。

### 4.5 交互方式（D20）

交互方式本身不含代码概念，在任何领域中都由同一组动作构成：

- 指着板子上的对象说话，而不是用文字描述它在哪里。
- 圈定任务目标；分别表达相关上下文与允许修改范围。执行是否被强制限制取决于宿主能力，板子不把选区自动升级为访问权限。
- 用混合表述提示修改意图；AI 交回目标版本，由人接受、调整或拒绝。
- Sand Table 提供了哪些上下文、Agent 通过其工具读取了什么，人看得见，也改得了；宿主其他上下文可能不可见。

简单的一问一答仍用宿主的对话框。函数、提交、PR 等概念属于代码领域包，不进入这组动作。

### 4.6 总览、任务、工作区与活动位置（D22、D23）

白板不是一个 Agent 工作区的镜像。白板组织整体上下文，任务关联相关对象，Agent 绑定实际工作区，活动再映射回相关对象。

| 概念 | 范围 | 示例 |
|---|---|---|
| 白板范围 | 用户关注的整体，可以跨仓库、系统和资料 | 前后端、服务、接口文档、当前任务 |
| 任务范围 | 本次希望解决的问题及相关对象 | 修复登录，涉及前后端与接口约定 |
| Agent 工作区 | 实际读取、写入和执行的环境 | 某仓库的一份 worktree、分支和工作区状态 |
| 当前活动位置 | 此刻正在检查、修改、测试或等待的对象集合 | 修改校验函数；随后运行跨模块测试 |

一项任务可关联多个工作区和多个 Agent；一个对象可在多种视图出现。逻辑对象身份与“某工作区中的某版本实例”分开，防止不同分支或 worktree 的内容与结果混淆。

工作区绑定至少说明环境身份、仓库、worktree／根位置、分支或 detached HEAD、源码内容状态。板子读取环境与 Agent 执行环境不同，需要显式映射；无法确认对应关系时不得声称结果验证了板上对象。

选区表示当前关注，阅读范围表示需要的上下文，修改范围表示本次请求允许改变的对象；三者分别表达。例如选中后端模块修改时，可以阅读接口文档，但不自动授予修改前端的意图或权限。

## 5. 组件体系

### 5.1 基础组件、可组合能力、场景预设

采用三层组织：

- **基础组件**：文本、资源、图表、表格、状态、代码、容器等可复用展示与交互。
- **可组合能力**：引用、详情、操作、AI 上下文、容纳、比较等。
- **场景预设**：由基础组件和能力组成的项目白板、Bug 修复白板等。

预设不是写死的业务流程。用户可以增删组件、改编排、配置数据和请求 AI 调整。

### 5.2 通用组件目录

| 类别 | 组件 | 第一领域用途 |
|---|---|---|
| 容器 | 普通白板、分组区域 | 项目、功能和任务组织 |
| 说明 | 文本、标题、便签、批注 | 背景、疑问、约束和局部解释 |
| 资源 | 文件、文档、图片、音视频、链接卡 | 文档、截图、复现材料和输出 |
| 数据 | 指标、状态、图表、表格、事件流 | 检查状态、执行统计和运行变化 |
| 工作 | 任务、清单、Agent 活动、操作面板 | 任务拆解、执行和人工介入 |
| 推理 | 问题、证据、比较、方案、决策、行为约定 | 区分问题、证据、取舍和结论 |
| 意图 | 意图 diff、目标版本 | 汇总人的混合表述；展示 AI 整理的修改以待确认 |
| 导航 | 对象引用、白板入口、局部视窗 | 深入局部与跨视图定位 |

### 5.3 代码开发领域组件

| 组件 | 摘要 | 深入后展示或执行 | 关键关联 |
|---|---|---|---|
| 项目／仓库 | 用途、git 版本、工作区状态、覆盖范围 | 文档、入口、依赖与贡献说明 | 仓库身份、提交、工作区 |
| 功能／模块 | 用户用途、输入输出、状态 | 调用路径、实现、接口与测试 | 功能—实现—验证 |
| 代码引用 | 文件、符号、片段及说明 | 固定版本源码、编辑器定位 | 路径、符号、版本、内容摘要 |
| 需求／任务 | 目标、进展、阻塞 | 方案、约束、验收条件 | Issue、行为约定、目标版本 |
| 行为约定 | 现在与期望的行为 | 输入示例、反例、不变条件 | 复现、测试和预览 |
| Agent 活动 | 执行者、当前工作、等待原因、更新时间 | Agent 报告的操作、实际工作区、上下文引用和产物 | 任务、工作区、活动对象集合、目标版本 |
| 工作区入口 | 仓库、分支／worktree、来源新鲜度 | 对应环境与源码状态、关联任务和 Agent | 工作区绑定、实际内容快照 |
| 变更／Diff | 修改范围、目的、状态 | 文件级与片段级比较 | 基础版本、目标版本、任务 |
| 运行／测试 | 状态、结果、耗时 | 命令、环境、日志、失败定位 | 实际工作区及被测内容快照，不只标记 HEAD |
| 预览／成果 | 页面、截图、输出文件 | 交互预览、附件及反馈 | 构建、运行、对应版本 |
| Issue／讨论 | 问题、标签、讨论状态 | 复现、已有意见、相关变更 | 来源与读取时间 |

对外提交相关组件（PR／审查、贡献约定）随 D18 的提交功能再做。

Agent 活动只展示 Agent 在本次会话中通过 Sand Table 工具报告的操作、状态、简要说明和公开输出，不要求获取或生成模型的隐含思维链。没有可靠状态来源时显示未知或断开，而不是用动画伪装正在工作。

### 5.4 组件类型声明（内部）

组件类型在代码内部声明以下内容。这是内部契约，不是对外 SDK（D01）：

- 稳定类型标识、默认尺寸和可用呈现层级。
- 支持的数据类型、详情渲染、比较、容纳能力。
- 可提供的动作及其前置条件。
- 对 AI 可读的语义摘要、允许修改的字段。
- 无障碍名称、键盘操作和加载、空白、错误状态。
- 不支持类型时的降级展示。

自定义分为配置、组合、代码扩展；代码扩展等第二个真实宿主出现再开放。未知组件显示可理解的占位与说明，不静默丢弃。

## 6. Metadata、来源与外部链接

### 6.1 元数据分组

| 分组 | 建议字段含义 |
|---|---|
| 身份 | 对象／实例 ID、类型、仓库或工作区身份 |
| 布局 | 所属白板、位置、尺寸、折叠、固定、布局约束 |
| 内容绑定 | 本地内容或数据引用、参数 |
| 来源 | 来源种类、原始位置、采集方式、采集者、版本 |
| 时间 | 发生时间、读取时间 |
| 新鲜度 | 当前 git 版本是否匹配、过期条件 |
| 可信状态 | 已观察、文档陈述、推断、人工确认、存在冲突 |
| 能力 | 可展开、可比较、可编辑、可执行动作 |
| 协作 | 内容作者、发起 Agent、目标版本状态 |
| 展示 | 摘要方式、主题覆盖、语义状态与无障碍标签 |

这些是逻辑分组，不意味着所有组件都要拥有所有字段。元数据只存在于本次会话中（D16）。

“人工确认”不保证事实永远正确；“AI 生成”不意味着必然错误。可信判断来自证据、版本和上下文，避免用一个不透明分数替代。

### 6.2 引用类型

- **来源引用**：解释或指标依据的文档、源码、API 或运行结果。
- **位置引用**：文件页码、代码符号、片段、日志区间。
- **对象引用**：另一个对象、白板或展示实例。
- **操作绑定**：由服务器注册的动作 ID、参数与执行条件。

代码定位建议保存仓库身份、提交或工作区修订、路径、符号信息、行区间及片段摘要。行号随编辑会变化，不能作为唯一身份。重命名和匹配失败必须显式报告，不能悄悄指向看似相似的代码。

操作绑定不是任意可执行脚本或隐藏在 URL 中的命令。

### 6.3 证据与过期

解释和关系可以引用多份证据，支持矛盾、失效与待核实状态。源码变化后（包括 AI 写入后），相关解释按新版本重新生成或标为需要重新检查；不要不加提示地沿用旧结论。

测试结果只能证明其实际执行的代码版本、配置和环境。工作区未提交变化应以工作区修订或内容标识关联，不可只记录分支名。

默认总览用短标签说明来源与新鲜度；展开后提供完整依据。演示数据与实际采集数据始终可区分。

## 8. 交互与视觉原则

### 8.1 工具箱

| 模式 | 主要行为 |
|---|---|
| 浏览 | 选择、悬停、聚焦、展开、跳转、查看关系 |
| 编排 | 拖动、缩放组件、分组、调整位置与明确关系、固定 |
| AI | 圈定范围、指着对象提问、查看并确认 AI 整理的目标版本 |

“解释、比较、定位”等直接动作与自然语言使用相同的命令模型和目标对象。文字输入使用宿主的输入框；板子上的文字说明进入意图 diff。不同模式应有清楚反馈；浏览时避免误拖，拖动和调整大小不触发业务执行，只有交给 AI 并经确认后才可能变成修改。

### 8.2 详情与渐进理解

远看展示用途、状态、异常和关键活动；展开后展示输入输出、来源、解释与动作。关系路径和详情面板可以临时浮现，不永久增加图上噪声。

支持“先讲用途”“举一个输入输出例子”“解释术语”“深入到实现”。解释围绕当前任务，既不假定用户会编程，也不把复杂行为简化成错误结论。

悬停不能是唯一信息入口，键盘聚焦和点击应能获取等价信息。本次会话中保留返回位置、阅读历史和局部锚点，避免用户在大图中迷路。

### 8.3 Agent 在总览中的呈现

- 选中 Agent 或任务时，以柔和区域或轮廓显示相关工作范围；这不是文件权限边界的替代。
- 在有证据关联的对象旁显示活动点、Agent 标识和短句，例如“正在修改校验逻辑”。
- 展开查看实际工作区、任务、最近操作、产物和等待原因。
- 多个 Agent 默认聚合展示，选中后展开，避免总览被大量活动点淹没。
- 一次活动可关联多个对象。无法定位时显示在任务或工作区入口，不能编造精确位置。
- 明确区分执行中、等待、断开和最后已知状态；记录来源及更新时间，不把过期报告持续画成实时工作。

### 8.4 主题

- 黑白主题：简洁、清晰、对比和留白，参考用户提出的 Apple／OpenAI 风格方向。
- 纸张主题：温暖纸色、柔和表面层级、适合长时间阅读，参考用户提出的 Anthropic／Claude 风格方向。
- 自定义主题：颜色、字体、密度、圆角、动效等配置；不改变组件语义和动作行为。

主题通过共享设计令牌作用于所有组件。状态同时使用文字或图形，不只靠颜色。高密度图优先可读性，运行提示只在有状态依据时出现；支持减少动效、足够对比度和键盘导航。

## 9. 架构规划

本节为规划方案。模块边界优先于具体包名和存储选型；保持通用核心可以脱离 GitHub、Research OS 或某个 Agent 独立使用。

### 9.1 分层与依赖方向

~~~mermaid
flowchart TD
    A["用户已订阅的 AI 客户端（宿主）"] --> B["对话与 Agent（宿主所有）"]
    A --> C["板子视图（MCP App，沙箱）"]
    B --> D["Sand Table MCP 服务器（本地进程）"]
    C --> D
    D --> E["总览与会话模型（内存）"]
    D --> F["代码开发领域与工作区映射"]
    F --> G["读取：git、文件、静态分析"]
    B --> H["Agent 实际工作区集合"]
    G --> H
    H --> I["Git 已记录的文件版本"]
~~~

| 层 | 职责 | 不应承担 |
|---|---|---|
| 宿主 | 对话、Agent、模型、登录、写文件与执行命令的权限 | 由 Sand Table 替代或复制 |
| 板子视图 | 画布、选择、布局、语义缩放、工具箱、详情；收集人的混合表述 | 直接写文件或执行命令 |
| MCP 服务器 | 向 Agent 暴露工具；向视图提供数据；在内存中维护本次会话的板子 | 持久化存储、保存凭据、主动启动 Agent |
| 通用核心 | 对象、白板、关系、视图、引用、意图 diff 与校验 | GitHub 字段、具体模型 API、Research OS 业务 |
| 代码开发领域 | 仓库、符号、路径、测试结果等对象与预设 | 重新实现通用画布 |
| 实际工作区与 Git | 工作区内容、已提交的文件版本 | 不自动保存白板状态或每次未提交写入 |

通用核心建议使用不依赖 UI 框架的数据与命令接口；首个 UI 实现可以沿用现有 TypeScript／React 技术基础。画布方案、MCP 服务器语言和代码结构来源仍待评估。

默认由 Agent 使用宿主自身的写文件能力写入，受宿主权限约束；Sand Table 服务器只读仓库。该边界决定 Sand Table 不能独立强制宿主的写入顺序与范围，见 11.3。总览可引用多个工作区；架构中的连接表示身份与数据映射，不要求白板范围等于任一工作区。

### 9.2 建议模块划分

| 建议模块 | 主要内容 |
|---|---|
| core | 类型与 schema、引用、关系、意图 diff、校验 |
| board | MCP App 视图：画布、选择、布局、导航、主题 |
| domain-code | 代码开发对象、关系、组件和预设 |
| server | MCP 工具、视图资源、git 与文件读取、静态分析调用 |
| plugin | 各家插件格式的清单与打包 |
| docs | 产品规范、架构决策、接口、验收与来源 |

这些名称不要求第一天就成为多个独立发布包。先维护清楚的依赖边界，避免为模块化增加过早的发布和构建负担。

### 9.3 逻辑数据契约

以下是接口讨论基线，不是已经冻结的 schema。所有记录只存在于 MCP 服务器进程的内存中。

| 记录 | 最小信息 | 约束 |
|---|---|---|
| ObjectRecord | id、type、content／binding、provenance | 与展示实例分离 |
| ComponentInstance | id、type、objectRef／localContent、boardId、layout、config | 不把坐标写回业务身份 |
| BoardRecord | id、成员、上下文策略、布局约束 | 容纳关系无循环 |
| RelationRecord | id、端点、type、assertion、evidence | 推断与已支持关系可区分 |
| ViewState | board、camera、filters、expanded、selection | 不改写外部事实 |
| SourceRef | 来源身份、工作区绑定、内容快照、定位信息、内容摘要 | 可检测失效与错配，不只引用分支名 |
| IntentDiff | id、基础白板修订、显式改动意图、文字说明、任务／读取／修改范围 | 整理可作为附带上下文，不自动转成改动请求 |
| TargetVersion | id、proposalRevision、workspaceBindings、baseSnapshot、具体补丁或目标文件内容、contentDigest、scope、说明、确认状态 | 确认绑定具体内容；前置条件变化后失效 |
| WorkspaceBinding | 环境／仓库／worktree 身份、根定位、HEAD、工作区内容状态 | 区分同仓库不同工作副本，环境间映射可核对 |
| TaskScope | 任务目标、相关对象、阅读范围、请求修改范围 | 与选区、白板边界及宿主权限分开 |
| AgentActivity | agentId、taskId、workspaceId、对象集合、操作、状态、来源、更新时间 | 未知与过期可见；不从布局推测执行位置 |
| BoardSession | sessionId、boardId、revision、视图绑定、工作区引用、活动时间、清理策略 | 独立于宿主对话与进程生命周期；仅存内存 |

Sand Table 不持久化任何记录，也不存放访问凭据。

### 9.4 权威来源

- git 和工作区决定真实代码与版本。
- 宿主拥有对话、Agent、模型选择、写文件与执行命令的权限。
- Agent 报告命令与运行状态；没有报告时，板子显示未知。
- Sand Table 只持有本次会话的板子。
- AI 生成的解释是带来源的投影，不能覆盖真实来源。

源码变化（包括 AI 写入后）触发相关部分重新生成。无法读取仓库时，显式标出读取失败和不可用动作。

### 9.5 状态与生命周期（D16、D27）

状态仅保存在服务器内存中，不建立持久数据库。必须区分白板实例、白板会话、视图实例、宿主对话、MCP 连接和服务器进程，不能假定它们同时创建或结束。

P0/P1 需明确以下规则：

- 使用显式会话、白板、视图和工作区标识路由请求；不同会话不混用选区、提案或确认结果。
- 关闭视图默认只解除该视图绑定；如果会话仍有效，重新打开可以恢复内存中的板子。
- 用户显式结束白板会话时清除状态；断线后在明确的可配置期限内保留，超时回收。具体期限在 P0/P1 决定。
- 进程退出后内存状态消失；重启或过期重开时提示重新生成，不能伪装成原板已恢复。
- 断线、视图刷新和资源销毁不是业务动作完成或取消的证据；不得因此重复写入。
- 多个视图或 Agent 同时操作时，以白板修订校验过期请求；这不是对外多人协作产品。

已提交文件由 Git 保存；未提交修改仍在实际工作区，不能声称已进入 Git 历史。宿主可能保留自己的聊天与工具结果，Sand Table 不控制其保留策略。测试材料由测试单独保存。可丢弃缓存是否允许落盘仍待决定，不通过“缓存”名称暗中持久化人工编排或确认记录。

### 9.6 宿主能力与实际连接（D24）

MCP 工具可用、MCP App 可显示、可以全屏、能读取本地仓库、Agent 能修改对应工作区，是分别需要验证的能力。第 12 节来源中的宿主呈现信息仅作为候选线索，不能作为完整产品兼容承诺。

| 验证项 | 必须得到的证据 |
|---|---|
| 服务连接 | 服务器运行在哪里，采用本地 stdio 或远程连接，实际安装与连接是否成立 |
| 视图能力 | 所选宿主及版本是否支持 MCP App、实际可用的显示模式与视图重开 |
| 工作区映射 | 白板引用的对象来自哪份代码，Agent 实际读写哪份工作区，环境间如何对应 |
| 选区传递 | 用户圈选后，Agent 下一次请求能取得哪一版选区和上下文 |
| 提案与刷新 | Agent 回复能定位回相关对象，源码变化后能刷新正确工作区的投影 |
| 状态与约束 | 活动来源、更新延迟；确认及修改范围是工作约定还是宿主强制机制 |
| 文字降级 | 无界面宿主能调用工具并完成对应文字流程；不冒充空间交互已验收 |

MCP Apps 规范将 UI 作为可选、需协商的扩展；MCP 传输规范区分 stdio 子进程与 HTTP 等连接方式。能显示板子不代表可以直接访问用户机器或复用全部开发能力。宿主能力记录需标明产品版本、测试日期、实际路径和未支持项。

P0 首先在一个具体宿主中验证“实际仓库 → 板子 → 圈选 → Agent 读取 → 局部解释”的链路。其他宿主保持待验证；多工作区的完整体验可以后续展开，但首个契约不能将一张白板硬绑为一个仓库。

### 9.7 可观察与可保证的范围

Sand Table 能校验自己提供的来源、自己的工具读取结果、提案身份和确认状态；能通过再次读取工作区观察实际差异。它不能仅凭一个 MCP 工具定义，强制宿主 Agent 的全部行为。

若宿主提供可靠的写入检查或权限集成，可以对具体宿主增加更强保证，并单独验证。未接入时明确标为工作约定与事后核对，不将其宣传为不可绕过的执行边界。

## 10. 仓库理解

### 10.1 建议分析流程

~~~mermaid
flowchart TD
    A["仓库身份与当前 git 版本"] --> B["文件／符号／文档索引"]
    B --> C["候选功能与结构关系"]
    C --> D["证据关联与不确定性检查"]
    D --> E["板子与解释"]
    E --> F["用户按需深入"]
    F --> D
~~~

具体职责：

1. 识别白板对象关联的仓库与实际工作区，包括环境、分支、提交、未提交变化、子模块和可用材料；多个工作副本分别标识。
2. 索引文档、配置、入口和受支持语言的符号；排除生成物与大体积无关内容时记录原因。
3. 在相同源码内容快照、分析配置和分析器版本下，确定性分析应产生稳定的基础对象身份与结构关系；再由 AI 提出面向任务的组织与解释。不要求同一提交对应唯一布局或唯一说明。
4. 将关系与原始证据关联，并标出动态调用、反射、插件、配置驱动行为等静态分析盲区。
5. 按用户问题按需深入，不把全部源码一次性塞进上下文。
6. 需要运行证据时，由 Agent 在其环境中实际运行并报告。
7. 源码变化后重新生成相关部分；本次会话中的人工组织尽量保持位置。

静态依赖图不等于实际调用轨迹；一次运行轨迹也不等于全部可能路径。两类数据在界面和模型中分别标明。

### 10.2 人工编排与 AI 整理

默认策略：

- 状态与来源数据可自动刷新，保持 git 版本可见。
- AI 可以提出新的解释、组件与关系，并在允许的局部自动维护摘要。
- 本次会话中，用户固定的位置、手动分组和阅读区域受到保护。
- 大范围重排、删除与语义关系改变以差异方案呈现。
- 用户可对某个区域开启更主动的整理，并随时收回。
- 用户编排在本次会话中作为意图线索；会话结束不保存。

更新应说明新增、失效、冲突和需要确认的内容。用户应能选择局部接受，不必在“全盘接受”和“全部拒绝”之间二选一；拆分接受时仍需验证依赖。

### 10.3 解释质量

每份重要解释记录适用工作区与内容快照、证据引用和未确定问题。需要支持输入输出示例、反例、失败路径、术语解释以及“我哪里还没看懂”的继续探索。

引用校验回答文件、符号和片段是否匹配，不自动证明自然语言结论成立。“引用有效”与“解释得到证据支持”分别显示和验收。新图与意图图对比可检查结构变化，但不能替代边界条件、输入输出、测试和运行验证；同样的图可能对应不同的程序行为。

不以 AI 自评代替质量检查。真实验收应检查关键路径是否遗漏、链接是否准确、用户能否用自己的话解释，以及面对反例能否识别解释的边界。

## 11. Agent 协作与动作模型

### 11.1 Agent 接入（D15）

Agent 是用户自己的，运行在宿主里，通过 MCP 连接 Sand Table。Sand Table 不启动或驱动 Agent，不持有模型凭据，不绑定模型供应商。

MCP 服务器向 Agent 暴露的工具，讨论基线包括：

- 打开或刷新板子（带 MCP App 视图）。
- 读取当前选区、圈定范围与相关上下文。
- 向板子写入带引用的解释和关系（仅本次会话）。
- 报告 Agent 当前的活动与产物（仅本次会话）。
- 读取意图 diff。
- 提交目标版本以供确认，并读取确认结果。

Agent 通过工具主动读取人的改动，作为支持相应 MCP 工具调用的宿主上的基本路径；实际连接与读取行为仍按 9.6 验证。不依赖界面主动发消息来保证基本工具流程；是否在支持的宿主中增加主动推送，见第 15 节。

### 11.2 统一上下文

直接动作与对话共同生成结构化上下文，包含：

- 用户意图、选中对象与区域，以及显式任务目标。
- 相关实际工作区绑定、Git 基线和涉及文件的内容状态；白板可引用多个工作区。
- 相关关系、证据、批注、行为约定与待决事项。
- 允许修改范围、固定组件与可用动作。
- 已截断或未读取的材料，以及上下文预算信息。

上下文不是整张板子的截图，也不是全部仓库内容的无差别复制。用户能检查 Sand Table 提供的上下文，以及 Agent 通过这些工具读取的内容；宿主系统指令、其他聊天和工具结果可能不可见，不宣称这是模型的完整上下文。AI 可以请求额外材料。

每次读取关联白板修订、选区和实际工作区身份，区分“已提供”“工具已读取”“Agent 自报已使用”，不把工具读取等同于模型已经正确理解。整理可作为关注偏好进入上下文；读取范围和请求修改范围单独列出。

### 11.3 意图、具体提案与写入（D17、D24、D25）

~~~mermaid
sequenceDiagram
    participant U as 用户
    participant B as 板子与只读 MCP 服务
    participant A as 宿主 Agent
    participant W as 实际工作区
    U->>B: 标记改动意图与范围
    A->>B: 读取意图及版本化上下文
    A->>B: 提交具体提案修订与修改内容
    B-->>U: 展示说明、差异与预期影响
    U->>B: 确认该提案修订
    A->>B: 读取确认与前置条件
    B->>W: 核对所涉文件实际内容
    B-->>A: 核对结果；是否强制执行取决于宿主
    A->>W: 使用宿主工具应用提案
    B->>W: 重新读取实际差异
    B-->>U: 映射回总览并报告一致或偏离
~~~

该图描述产品引导的工作流程，不是只读服务器对宿主的强制控制链。纯解释不需要额外确认；具体修改以提案为单位确认，不要求每写一行或每保存一个文件都弹窗。

目标版本至少包含提案 ID、修订号、实际工作区绑定、基础内容快照、具体补丁或目标文件内容、修改范围、内容摘要及说明。用户确认方案方向与用户确认具体修改内容是不同状态；方向确认不能自动被当作任意后续补丁的确认。

- 确认绑定提案修订和内容摘要。修改提案内容后，旧确认不再适用。
- 基础状态包含涉及文件的实际内容；Git HEAD 不足以识别未提交、暂存和未跟踪文件变化。
- 应用前核对相应文件的存在／缺失、内容以及操作前置条件；发现冲突则失效并重新整理，不静默覆盖。
- 核对与实际写入之间仍可能发生并发变化。没有宿主原子条件写入或等价保障时，必须承认竞态可能，不能声称已彻底阻止过期写入。
- 应用后重新读取差异，与已确认提案比较；偏离、部分完成或无法核对分别呈现，不自动算完成。
- 多工作区提案明确各自的基线和结果；不承诺跨仓库原子写入。
- 请求修改范围通过提案与实际差异检查。宿主没有强制机制时，越界只能被流程约定和事后核对发现，不能声称技术上不可能发生。

具体宿主若具备写入前检查机制，可增加更强约束；它必须有独立的能力声明和验证。首版无需为此自建执行平台。

### 11.4 状态、失败与 Git 记录

提案状态包括待确认、已确认、已拒绝、已失效，以及应用后的核对状态。结果区分未写入、部分写入、实际差异一致、实际差异偏离、无法核对；已写入不等于已提交。

命令、测试与写文件由宿主执行。板子展示来源与最近更新时间，明确区分运行、等待、断开和最后已知状态；Agent 未报告且没有其他可靠来源时显示未知。工具返回不等于业务成功，连接恢复不自动重做副作用操作。

Git 提交记录已提交的文件版本，不自动保留每次保存。是否每个确认提案形成一个提交仍在 P0 决定。未提交结果用实际内容标识与差异关联；需要长期回看时由宿主或用户显式提交或采用已有快照机制，Sand Table 不另建持久账本。

板子确认只覆盖对应提案，不能覆盖用户或其他工具随后产生的编辑。Git 已记录的内容可通过适当 Git 操作恢复；未记录内容不承诺可恢复。Sand Table 不承诺撤销外部业务动作。

### 11.5 访问边界

仓库文件、Issue 文本、日志和外部链接都是被分析的数据，不能自行扩大执行权限。MCP App 视图运行在宿主的沙箱中；服务器只读仓库，不持有凭据。

运行项目、安装依赖、发送数据到模型、写入文件分别由宿主的权限控制。界面应把必要的信息放在相关动作处，不用一套泛化弹窗阻碍正常阅读。

### 11.6 对外提交（以后，D18）

首版不提供对外提交。以后若提供，Issue 和 PR 都不设门槛。

提交前检查是一个开关，默认关闭，用户自己选择。打开时，对外草稿需先回答三问，有一问答不上来就不生成草稿：

1. 实际发生了什么？一句维护者能接受的话。
2. 这是观察到的，还是为了提交而摆出来的场景？
3. 维护者追问当时的情况时，能否不编造地回答？

关闭时，按用户要的 Issue 或 PR 直接生成草稿。开关不影响本地修改。草稿和发送是两个动作，发送由用户自己按下。

## 13. 分阶段开发规划

按可验收成果推进，不在尚未明确人员与范围时承诺日期。阶段可以迭代，但不得用后续愿景掩盖当前缺口。

### P0：技术选型与验收准备

**目标**：为第一个真实切片做好技术和验收准备（D21）。

交付：

- 技术选型记录：MCP 服务器语言与运行方式；板子在 MCP App 中的渲染方案；代码结构来源；第一个切片的宿主；目标版本与 git 提交的对应方式。
- 外部验收题目：选定外部仓库与过往 Issue，版本钉在修好之前；题目封存；评分标准事先写好（D19、14.3）。
- 按 9.6 验证一个具体宿主的连接方式、MCP App 呈现、实际仓库与执行工作区映射。
- 技术探针跑通“实际仓库 → 板子 → 圈选 → Agent 读取最新上下文 → 返回局部解释”；记录哪些能力为工作约定、哪些由宿主强制。
- 定义会话身份、内存清理规则和提案内容基线；明确 Git 提交不等于完整工作区状态。

通过条件：技术选择与实际链路有证据；对象引用和 Agent 工作区对应准确；题目与评分标准已封存；已得到开始功能开发的明确指令（D14）。本轮文档修改不启动技术探针或功能实现。

### P1：第一个真实切片——只读板子

**目标**：在一个选定宿主中，用户的 Agent 打开板子，用户能沿一条真实功能路径理解外部仓库。

交付：

- MCP 服务器与 MCP App 视图；至少一种宿主的插件格式可以安装。
- 首个切片先展示一个外部仓库的项目概览与一条功能路径；模型保留白板总览跨多个工作区的能力。展示用途、输入输出、关键路径、源码引用与确定程度。
- 标出 Agent 的任务、实际工作区和有依据的活动位置；可聚合、展开，支持关联多个对象及未知／过期状态。
- 浏览：选择、悬停、展开、搜索、按需显示关系、详情。编排：拖动、分组、固定（仅本次会话）。
- 圈定范围与指着对象提问；Agent 通过工具读取当前选区与上下文。
- 在不画界面的宿主中，同一组工具返回文字。

通过条件：在选定宿主中实际链路可用；在一个无界面宿主中文字流程可用；关键断言的引用可追溯到对应工作区内容，解释的语义正确性另行核对；不同分支／worktree 的对象与活动不混淆；推测与已确认可区分；显式结束或到期清理后无 Sand Table 持久状态；首批语言与解析范围明确。

### P2：从意图到修改

**目标**：用户用混合表述指导 AI 完成一个外部仓库中可复现 Bug 的局部修改。

交付：

- 意图 diff：区分整理与改动请求；保留前者作为可见的背景上下文。
- 目标版本：具体提案修订、工作区内容基线、补丁／目标内容、修改范围和说明；确认绑定具体内容。
- 按已验证的宿主工作流程应用提案，写入前检查实际内容，写入后核对真实差异并局部更新总览；异常结果明确显示。
- 测试与运行由 Agent 在其环境中执行并报告，绑定实际工作区、被测内容和环境，不仅绑定提交号。
- 白板嵌套与对象多实例（D03）；黑白与纸张皮肤、基本自定义主题（D09）。

通过条件：人的编排不直接改文件；所选宿主的受测流程按已确认具体提案工作；陈旧提案、未提交变化和实际差异偏离可检测；没有强制机制的约束明确标为工作约定；已提交结果能在 Git 定位，未提交结果不冒充提交；测试与实际内容对应；失败或未知状态不显示为成功。

### P3：第一个能用版本的检验

**目标**：判断产品做得好不好，以及板子是否比对话框好。

交付：

- 外部基准：在封存题目上执行修复与独立验证；产物匿名化后由不知道来源的评分者评估，历史合并结果作为参考（14.3）。
- 纯对话对照（14.4）。
- 第二领域检查（14.4）。

通过条件：任务、评分标准、操作者安排和资源条件事先固定；可比产物采用同一形式并匿名化；避免同人先后完成同题的学习效应；不向外部仓库发送内容；修复、理解与交互收益分别记录，包括不如对话或历史参考的情况。

### 后续（未排期）

- 对外提交（D18、11.6）。
- 第二个真实宿主出现后：对外组件 SDK、配置迁移、嵌入示例（D01）。
- 更大仓库、多语言、更多宿主；增量索引、视口虚拟化、上下文成本与性能优化。
- 研究实验、基础设施运维、教学／知识、创作等领域包。服务器负载、可用性、资源分配和服务状态组件属于领域扩展，不应反向占据通用核心。
- 基于 git 历史的过程视图（若第 15 节决定恢复 D07 的一部分）。

在首个代码领域中，文件版本交给 Git，实际工作区另有未提交状态。扩大领域前，用至少一个非代码场景检查通用核心是否夹带函数、PR 或 Git 假设；其他领域的权威来源由其接入系统提供，不把“必须以 Git 文件表达”写入通用交互契约。

## 14. 验收与测试策略

### 14.1 证据类别分别保留

| 类别 | 证明什么 | 不能替代什么 |
|---|---|---|
| 模型与接口测试 | 关系、引用、作用域和目标版本约束正确 | 用户是否能理解 |
| 宿主内交互验证 | 板子在宿主中的操作、主题和详情可用；无界面宿主的文字可用 | 真实数据与执行真实性 |
| 外部仓库集成验证 | 引用、分析、修改和运行链路实际成立 | 未测试仓库的普遍正确性 |
| 外部基准与对照 | 修复质量与当时结果、与纯对话相比如何 | 所有代码语义已被证明 |
| 初学者真人验收 | 用户能独立理解、判断和推进任务 | 修复质量的普遍结论 |

测试围绕具体风险，不把截图数量或测试通过率作为产品价值的替代指标。界面和交互方式发生根本变化后，旧人工验收记录只能说明旧版本。

### 14.2 关键正确性检查

- 白板无容纳循环，同对象多实例保持数据一致。
- 删除展示不会删除实际资源；错误引用不会静默重定向。
- 人的编排不直接写文件；确认绑定具体提案修订；实际内容变化会使前置条件失效。
- 对受测宿主分别验证工作约定与强制保障；不声称只读服务器控制所有写入。
- 应用后核对具体差异，部分完成、越界或无法核对均不冒充成功。
- 依赖关系、证据关系和编排关系不会混淆。
- 测试、预览和解释绑定正确的工作区与内容快照，包括未提交变化。
- 相同输入和分析配置的基础对象及结构关系稳定；布局可随任务变化。
- 引用有效、解释正确、结构意图落实和行为验证分别检查。
- Agent 状态显示有真实来源；没有来源时显示未知。
- 显式结束或到期清理后无 Sand Table 持久状态；视图重开、断线、并发请求和进程重启遵循已定义生命周期。
- 总览中的多工作区、多分支与多 Agent 映射准确；活动位置、等待、断开和最后已知状态不混淆。
- 不画界面的宿主中，工具文字仍给出完成任务所需的信息。
- 中文输入法、键盘操作、焦点和减少动效能够正常工作。
- 模拟数据与当前数据可区分。

### 14.3 外部修复基准与评分者盲评（D13、D19、D29）

使用已合并的外部 Issue／PR 形成题目，仓库固定在修复前版本；求解时隔离后续答案，不搜索原 PR。题目、可见材料、环境和评分标准事先封存，记录模型可能见过公开题目的污染风险。采集日期晚于训练截止不能单独证明原问题或答案未被模型见过。

区分三种产物角色：

- 纯对话条件下完成的修复。
- Sand Table 条件下完成的修复。
- 当时已合并的历史修复，作为参考产物，不当作条件一致的第三个实验组。

修复质量通过隐藏测试、回归检查、修改范围及可读性评估。测试覆盖边界和环境差异应记录，不用“测试通过”替代全部语义正确性。历史 PR 不是唯一正确实现，评分不以代码相似度为目标。

将补丁和维护者说明整理成统一形式，去掉来源标记并随机编号后交给评分者。准确描述为“答案隔离、产物匿名化、评分者盲评”；操作者知道所用界面，不宣称整个实验双盲。

修复正确不能证明讲解正确。另行检查源码引用有效性，并由评分者抽查关键解释是否得到证据支持。基准材料由测试单独保存，不属于产品状态；验收不向外部仓库发送任何内容。

### 14.4 交互对照、理解评估与第二领域检查（D20、D21、D29）

在第一个能用的版本上分别回答：

| 问题 | 主要证据 |
|---|---|
| 修复质量如何 | 隐藏测试、回归检查、修改范围和产物审查 |
| 用户是否理解 | 自己复述路径、解释依据、识别错误和预测具体输入下的行为 |
| 白板是否优于纯对话 | 条件受控的交互对照，比较完成、错误识别、上下文恢复和重复表达 |

交互对照尽量固定 Agent／模型版本、可用工具、仓库材料、任务要求、时间与调用预算，并记录无法保持一致的部分。改进后的工具如果只提供给白板条件，应说明比较的是整套产品收益，而不纯粹是界面收益。

避免同一个人先用一种界面再用另一种界面完成同一道题：采用难度相近的不同任务交叉安排并平衡顺序，或者让不同用户处理同一道题并记录经验差异。操作者是否为初学者事先明确；开发者自己的测试不能代替初学者证据。

“发现几次 AI 错误”同时记录实际出现多少可识别错误，避免错误更少的一组反而看似更差；“隔天找回上下文”注明宿主保留了哪些聊天或材料以及 Sand Table 的瞬时状态限制。记录是否完成、用时、错误识别、重复描述／复制粘贴、人工帮助和实际资源消耗。

这些是早期证据，不用一个任务或两位用户的结果宣称普遍取代对话。

第二领域检查继续在第一个可用版本进行：使用同一组通用动作完成非代码任务，例如比较两次研究实验。检查核心是否混入代码工作区或 Git 假设；不要求重新建立持久化系统。

### 14.5 初学者真人验收

建议首轮至少邀请两位未参与实现、缺少相关仓库经验的用户；人数是形成早期反馈的规划下限，不代表统计性证明。

用户在固定构建与固定版本的外部仓库上：

1. 说明项目用途和一个真实功能的输入输出。
2. 追踪该功能的关键路径，并指出至少一处来源。
3. 识别一条 AI 推断或证据不足的解释。
4. 描述一个复现问题，建立期望行为和不变条件。
5. 用拖拽加文字表达一处修改意图，判断 AI 复述的意图是否正确。
6. 通过 Diff、测试和更新后的板子判断结果，指出尚未验证之处。
7. 指出 Agent 实际操作的工作区和当前活动，区分不同分支或工作副本。
8. 对已提交结果在 Git 历史中定位；对未提交结果识别当前差异及其未持久记录的限制。

记录完成情况、理解错误、人工帮助、用时、迷失位置、对 AI 错误结论的识别情况。主持人代写命令或解释架构属于辅助，不能计为独立完成。

### 14.6 性能与规模

P0/P1 需确定可重复的性能场景：宿主、目标设备、仓库规模、可见／总组件数量、边数量及展开深度。分别测量首次可交互、平移缩放、搜索、详情加载、索引更新和内存。

具体数字目标在原型测量后冻结，避免在无依据时承诺“无限画布”性能。大型仓库使用局部加载和可见范围渲染，不能要求一次性加载所有源码与所有组件。工具结果需控制在宿主的大小限制内。

### 14.7 阶段完成规则

每阶段记录实现提交、支持范围、测试与真人证据、已知缺口和下一步。功能可见、实现合并、自动检查通过、真人验收通过、基准结果分别记录，不互相替代。

## 16. 后续开发约定

- 从用户旅程和验收条件拆分 Issue，每项关联本文的具体目标。
- 对对象身份、意图与目标版本、宿主边界、工具接口等重大改变建立架构决策记录。
- 每个实现 PR 说明解决的问题、行为变化、验证方式和实际限制。
- 示例数据和真实连接分别标识，不将演示能力写入已支持清单。
- 核心、领域包、视图与服务器之间的依赖方向由代码审查和必要自动检查维护。
- 引入第三方代码时固定来源与许可，验证适配范围，不直接继承外部项目全部规则。
- 任何对外发送遵循 D18；验收与基准不向外部仓库发送内容。
- 原 README 的旧运行方式在替换实现前保留说明；新能力就绪后再更新面向用户的入口。
- 任何设计调整都应保留这里最重要的目标：让用户形成自己的理解与判断，并能据此指导 AI。

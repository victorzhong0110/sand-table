# 历史时间线：撤销到任意一条记录

> 契约版本 v1（2026-10-20）。本文是「撤销到某条只支持栈内记录」这条缺陷的修复规格。
> 相关 issue：#11 的 P3 后续项。

## 1. 问题

现在的历史是**两个栈**：撤销栈（已应用）与重做栈（已撤销）。

```
record(e)  → 压入撤销栈，并**清空重做栈**
```

后果：一旦「撤销 → 做了新编辑」，被撤销的那段历史被永久丢弃。
用户之后再也跳不回那段状态——尽管它曾经真实发生过、且板面内容仍然记得。
更麻烦的是「跳到某条记录」只能跳到**当前还留在栈里**的记录，
一旦被清空，UI 上那条记录消失，用户连「想跳回去」都做不到。

这不是 UX 问题，是**模型问题**：历史被当成了一条随时可丢弃的栈，
而不是作品生命过程的记录。

## 2. 模型：分支时间线

历史是一棵**树**，不是两个栈。

```
        e1 ── e2 ── e3          ← 当前分支（游标在 e3）
             \
              e4 ── e5          ← 撤销 e3 后从 e2 分叉出来的新编辑
```

- 每条记录带 `parentId`：它是在哪条记录之上发生的。
- 有一个**游标** `cursorId`：当前板面处于哪条记录之后。
- 新编辑**从游标分叉**：旧分支原样保留，仍可跳回。

`TimelineEntry` / `TimelineState` 的类型定义在 `core/objects.ts`（共享契约，负责人维护）：

```ts
export type TimelineEntry = HistoryEntry & {
  parentId?: string;
  seq: number;
};
export type TimelineState = {
  version: 2;
  entries: TimelineEntry[];
  cursorId?: string;
};
```

## 3. 四个动作的语义

| 动作 | 语义 | 返回 |
|---|---|---|
| `record(e)` | 追加一条记录；若与游标处记录满足合并条件（同 intentId、连续、上一次不是 undo/redo），则**合并进游标那条**而不是新增 | 合并后的条目 |
| `undo()` | 游标移到当前记录的父节点；板面回退 | 被撤销的条目；无父节点时返回 undefined |
| `redo()` | 游标移到某个子节点；有多个子节点时取**最近创建**的那个 | 被重做的条目 |
| `jumpTo(id)` | 游标移动到任意记录：先沿父链回退到**最近公共祖先**，再沿子链前滚到目标 | `{ undone, redone }`，与现有接线一致 |

### 3.1 跳转到任意记录

跳转要跨分支，所以必须是**路径重放**：

```
jumpTo(target):
  1. 找 current 与 target 的最近公共祖先 lca
  2. 撤销段：从 current 沿 parent 链回退到 lca，收集 undone
  3. 重做段：从 lca 沿子链前滚到 target，收集 redone
  4. 游标 = target
```

`undone` / `redone` 的顺序必须与现有 `core/store.ts` 的接法一致：
先应用 `undone` 的 before 快照，再应用 `redone` 的 after 快照。
**顺序错一次，板面就会串**（上轮已经踩过：跳到「已撤销」那条记录时先把撤销栈撤完，
结果变成「回到起点」）。

### 3.2 分叉后 redo 走哪条

同一父节点下可能有多个子（新分叉）。`redo()` 取**最近创建**的那个，
并在文档与 UI 上说清楚「重做回到你上次走的那条路」。

## 4. 意图分组仍然成立

「一次连续输入算一步」是 v1 就要保住的行为，不能因为换模型丢掉：

- 合并条件不变：同 `intentId`、与上一次动作连续、且上一次不是 undo/redo。
- 合并后仍是**一条**记录，撤销一次全部回退。
- 撤销/重做会打断合并（`mergeable = false`）——分叉后在新分支上继续输入，
  不会跟旧分支的记录粘在一起。

## 5. 拒绝与审计的语义不变

- 外部效果（如「已发布」「已运行实验」）仍然**不进撤销栈**，
  但要留在 `refused` 列表里让人看见（上轮的教训：拒绝必须可观测）。
- 缺 `kind` 的条目在严格模式下同样被拒绝；非严格模式放行但记进 `unclassified`。
- 审计日志与撤销导航严格分离，审计只追加。

## 6. 持久化与迁移

工作空间文件里的 `history` 字段形状变了：

| 版本 | 形状 | 处理 |
|---|---|---|
| v1 | `{ undo: HistoryEntry[], redo: HistoryEntry[] }` | 迁移：把 undo 栈按顺序串成一条链（后一条的 parentId 指向前一条），游标落在最后一条；redo 栈里的记录**也保留**——挂在 undo 栈最后一条之下作为分支，避免迁移丢历史 |
| v2 | `{ version: 2, entries, cursorId }` | 直接读 |

- 迁移在 `core/workspace.ts` 的迁移链里（负责人维护），版本号递增。
- 迁移**不得丢记录**：v1 的 redo 栈必须落到 v2 的 entries 里。
- 写回时统一写 v2。

## 7. 容量

文件会随分支增长。规则：

- 保留上限默认 **500 条**（可配置）。
- 裁剪只从**叶子**开始（没有子节点的记录），
  且**绝不裁剪当前游标所在路径上的记录**。
- 裁剪后游标必须仍然有效；若游标指向被裁掉的记录，把游标上移到最近的祖先。

## 7.1 容量的取舍（实现后回写）

规格要求「保留上限 500 条」且「绝不裁剪当前游标所在路径上的记录」——这两条在**线性历史**里互相矛盾：
没有分叉时每条记录都在游标路径上，一条也裁不掉。

实现的取舍：

- **内存里的时间线不裁剪游标路径**（撤销永远能退到底）✓；
- 真正被裁掉的是**被分叉取代、已经不在任何路径上的旧分支** ✓——那才是「文件随分支增长」的部分；
- 因此**线性历史的工作空间文件会一直增长**，与换模型之前的行为一致（v1 也是线性增长，
  只是它会丢掉重做栈）。

这条取舍如实写在这里，不假装 500 条上限已经生效。
下一步要做的是给**持久化层**加窗口（只保留最近 N 条落盘），
代价是超出窗口的最早记录重启后不再可达——那属于格式演进，要单独设计。

## 8. UI

历史面板（`board/HistoryPanel.tsx`）从「两列列表」改为**单条时间线**：

- 全部记录按 `seq` 排序显示，当前位置高亮。
- 已被分叉取代但仍可达的记录要能看见并能跳过去（标注「旧分支」）。
- 每一行显示：标签、时间、人还是 Agent、是否可撤销。

## 9. 不变量

| 编号 | 不变量 | 怎么验 |
|---|---|---|
| T1 | 撤销后新编辑不丢旧历史 | 撤销一次 → 新建一个 → 跳回被撤销那条，内容仍是撤销后的样子 |
| T2 | 任意记录都能跳到 | 造 5 条记录，随机跳到每一条，板面内容等于该记录刚发生时的样子 |
| T3 | 跨分支跳转正确 | 在分支 A 与分支 B 之间来回跳，两边内容各自正确，不串 |
| T4 | 一次意图仍然是一步 | 连续 3 次输入 → 一次撤销全回退 |
| T5 | 撤销不震荡 | 连续两次 undo 拿到两条不同记录；undo→redo→undo 结果一致 |
| T6 | 外部效果仍不入栈 | 外部条目被拒且出现在 refused 里 |
| T7 | 迁移不丢记录 | v1 文件迁移后记录总数 ≥ 原 undo+redo 总数，且都能跳到 |
| T8 | 裁剪不破坏游标 | 大量编辑后裁剪，游标仍有效，历史仍可跳 |
| T9 | 落盘后重开仍能跳 | 保存→重开→跳到旧记录成功 |

## 11. 与旧契约的关系

`docs/architecture/workspace-kernel.zh-CN.md` 的 I10（撤销栈与重做栈分离）被本契约取代：
**双栈 → 分支时间线**。I10 的原意（审计与撤销导航分离、撤销不震荡）继续有效，
取代的只是「历史用两个栈存」这个实现形状。内核契约需同步改写该条。

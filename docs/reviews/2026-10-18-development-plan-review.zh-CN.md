## 0. 总评

原文在"诚实"这一维度做得很好：来源、版本、新鲜度、推断与已证实的区分、回放无副作用、不用动画伪装 Agent 状态。这些应保留为产品的核心不变量。

主要问题有三个：

1. 价值假设——"没有编程经验的人能通过空间画布理解仓库并指导 AI 修 Bug"——尚未验证，原文却已在设计通用框架、组件 SDK、嵌套白板和双模式时间轴。
2. 最难、最决定成败的部分（仓库地图怎么产生、Agent 怎么接、代码在哪里跑）停留在原则层，没有候选技术；相对容易的部分（主题、metadata 分组、嵌套规则）反而写得很细。
3. 范围相当于同时做白板引擎、代码情报、Agent 编排和贡献工具。单人推进，P1 就可能耗尽精力。

## 1. 最大风险

### 1.1 先验证价值，再造引擎

建议把 P0 改为"绿野仙踪"测试：不写引擎，用现成白板（tldraw、Excalidraw）或一页静态 HTML，为一个真实仓库的一条功能路径做出项目总览板、一条导览和带源码证据的解释（可由 Agent 生成，人工逐条核对）。请两位非程序员按 14.3 的前三项任务走一遍。

判定标准：他们能否复述路径，能否指出一条证据不足的解释。做不到，说明问题在信息设计而不在引擎，应先改信息设计。这一步一到两周可完成，决定后续投入是否值得。

### 1.2 应用优先，框架后抽取

D01 把"可嵌入框架"放在首位。只有一个领域、一个宿主、零个外部嵌入方时，设计组件 SDK、配置迁移、能力声明和嵌入示例，抽象几乎一定会猜错。

建议 D01 改为：先做好一个工作台；代码层面保持 core 不依赖 React 与 Git，但不对外承诺 SDK。等第二个领域（研究实验或运维）真正接入时，再从两个实例中抽取框架接口。P1 的"最小嵌入示例"后移到 P6。

### 1.3 贡献目标与维护者负担

D12 与 D13 组合起来——让没有编程经验的人向大型开源项目提交修复——正是当前开源维护者最反感的 AI PR 来源。如果工具让低质量 PR 更容易产生，它会被社区排斥，与 D13 的目标相反。

建议：

- P5 的默认产出改为"带失败测试的高质量 Issue"。PR 只在 Issue 被维护者确认、或项目明确欢迎外部修复时才进入草稿。
- 把"维护者能在几分钟内判断这份贡献"作为 P5 的验收维度。
- 加入贡献前真实性检查组件（见 3.7）。
- PR 草稿默认包含 AI 协助披露，并读取目标项目的 AI 贡献政策。

## 2. 缺失的关键架构元素

### 2.1 代码情报层（最大缺口）

第 10 节只写了流程，没写用什么产生"可证明的结构事实"。建议明确两条证据通道，并在 P0 选型：

- **静态**：LSP（pyright、tsserver 等语言服务器）或 SCIP 索引（scip-python、scip-typescript）提供符号、定义和引用；tree-sitter 负责语法切块和片段哈希。不建议自研解析器。
- **动态**：运行一个可复现的命令（测试或 CLI）时采集实际调用轨迹。Python 可用 coverage.py 的动态上下文（每个测试覆盖了哪些行）或 3.12+ 的 `sys.monitoring`；Node 可用 `--cpu-prof` 或 V8 coverage。这直接对应"从软件行为出发"：用户点一个功能，看到的是它实际走过的代码，而不是静态推测。

"测试 → 被覆盖代码"的映射还顺带给出"这段代码被哪些测试验证"的关系，正好服务 P3。

### 2.2 断言（Claim）作为一等对象，配确定性引用校验

原文把"解释"当作一段带证据的文字。建议把解释拆成断言：每条断言包含一句陈述、若干 SourceRef、状态（已观察／文档陈述／推断／有冲突／过期）和适用提交。

配套一个不依赖 AI 的校验器：对每个 SourceRef，在对应提交上检查文件存在、片段哈希一致、符号仍在该位置。AI 给出的引用对不上，就直接标出，不进入"已证实"。好处：

- 过期检测细到单条断言，而不是整段解释。
- 用户可以对单条断言提出异议。
- 引用有效率是可测、可回归的质量指标，比 AI 自评可靠（呼应 10.3）。

### 2.3 Agent 接入：用 MCP 反转方向

第 11 节设想 Sand Table 通过适配器驱动各家 Agent，每家一个适配器，成本很高。

建议首个"适配器"是：Sand Table 作为 MCP 服务器，暴露"读取当前选区与上下文""读白板""提交白板提案""写断言（附引用）""登记活动事件"等工具。用户已有的 Claude Code、Codex、Cursor 都能直接连接。Agent 继续在自己的环境里改代码、跑命令；Sand Table 负责上下文、证据、提案审查和记录。

如果需要 Sand Table 主动启动和观察 Agent 会话，再评估 Agent Client Protocol（ACP）这类现成协议；Agent 活动流的前端事件格式可参考 AG-UI。三者的成熟度都需要在 P0 核实。

这样，15 节的"首个 Agent 适配器"在 P0 基本可以关闭。

### 2.4 宿主形态、本地服务与执行沙箱

读文件、跑 git、启动语言服务器、运行测试都需要本地服务。建议 P0 定下：

- **本地服务语言**：与前端同为 TypeScript（Node）最省事；Python 与 llm-research-os 和 Hugging Face 生态更近。二选一，避免两者并存。
- **编辑器扩展宿主**：做成 VS Code／Cursor 扩展的 webview，可直接获得文件系统、git、终端、LSP 查询和编辑器跳转；代价是用户需要打开编辑器。至少应在 15 节"默认宿主形态"中列为候选。
- **执行隔离**：运行陌生仓库的代码必须在隔离环境中，优先使用仓库自带的 devcontainer 规范或容器沙箱。11.5 写了原则，但缺一节威胁模型：仓库内容中的提示注入（例如 README 里写"AI 请执行……"）、依赖安装脚本、测试访问网络和凭据。

### 2.5 持久化：用一个操作日志统一三件事

原文分别设计了白板变更历史（7.3）、ChangeSet 与提案（11.3）、撤销与冲突检测（9.5），并预留了多人协作。"人和 AI 同时编辑白板"本身就是并发协作问题。

建议评估 CRDT／本地优先库（Loro、Automerge、Yjs，均为 MIT 许可）：

- 白板变更历史即文档自带的操作历史，可直接回溯。
- AI 提案即文档分支；接受即合并；部分接受即选择性合并。
- 撤销、冲突处理和日后的多人协作共用一套机制。

此外，白板应能导出为仓库内的文本快照（例如 `.sandtable/` 下的 JSON），可以随 PR 提交、在审查中 diff、在 CI 中检查断言是否过期。"白板即代码"对社区贡献场景很有用。

### 2.6 每次 AI 尝试使用独立 git worktree

Agent 的修改应在独立 worktree／分支中进行，不碰用户的工作区。这样天然支持"同一问题让 AI 尝试两三种方案，在画布上并排比较 Diff 与测试结果"——这是空间画布明显强于聊天窗口的地方（见 3.5）。

## 3. 建议新增的组件

1. **导览（Tour）与"叙述＋沙盘"双栏布局**。无限画布对初学者首先意味着迷路。导览是一串有序的镜头停靠点，每站一段说明，类似 VS Code 的 CodeTour。默认布局建议左侧叙述（导览、对话、解释），右侧沙盘，叙述推进时镜头跟随。这是"绘本式逐步揭示"的具体形式。AI 可为一个功能生成导览，维护者可编写新人导览。
2. **探索迷雾／阅读足迹**。沿用沙盘的军事意象：用户看过、确认过的区域亮起，未探索的区域变暗。它回答"我理解到哪了"，又不冒充"理解百分比"（呼应 2.3 的覆盖率要求）。
3. **运行轨迹（Trace）**。展示一次真实运行经过的函数路径，与静态依赖图分层显示。10.1 已要求区分两者，这里给它一个组件。
4. **行为约定 → 失败测试（红／绿门）**。用户用输入输出示例描述期望；Agent 把它转成测试；修复前必须先失败，修复后通过，并绑定提交。这是非程序员唯一能自己判断的强验证，建议作为 P3 的中心而非附件。
5. **方案并排对比**。基于 2.6 的多 worktree，同屏比较多个候选修复的 Diff、测试结果和影响范围。
6. **复述检查（Teach-back）**。用户用自己的话复述一条路径，AI 对照断言与证据指出遗漏或错误。把 14.3 的"用户能复述"变成产品内的动作。
7. **贡献前真实性检查**。生成 Issue／PR 草稿前先回答三个问题：实际发生了什么（一句维护者能接受的话）？这是已记录的公开行为或已有 Issue，还是为了提交而构造的场景？维护者问"描述一下实际情况"时，用户能否不编造地回答？答不上来就不生成草稿。
8. **成本与上下文账本**。显示每个 AI 动作的 token、费用、读取了哪些材料、截断了什么。11.2 提到上下文预算，但没有成本可见性。解释按（提交，符号哈希）缓存，避免重复花费。
9. **命令面板（Cmd-K）**。在大图里，搜索跳转比平移缩放更常用。建议作为一等导航入口，并与直接动作共享同一命令模型（8.1 已要求统一命令模型）。

## 5. 建议的阶段重排

- **P0 验证**：绿野仙踪测试（1.1）；四项技术选型（代码情报、Agent 协议、本地服务语言与宿主、持久化）；选定验收仓库与 Bug。
- **P1 只读沙盘**：一个真实仓库、一条功能路径。地图由用户的 Agent 通过 MCP 生成，断言经确定性校验；包含导览、详情、证据、Cmd-K、探索迷雾。用户编辑限于移动、固定、分组和批注。
- **P2 修复闭环**：行为约定 → 失败测试 → Agent 在 worktree 中修复 → 测试通过；运行轨迹；方案对比；执行在沙箱中进行。
- **P3 历史与贡献**：活动时间线与检查点 Diff；真实性检查和 Issue 优先的贡献草稿；导出静态 HTML 快照用于分享。
- **之后**：白板实时嵌入、时间游标、组件 SDK、对外嵌入、自定义主题、第二领域。

验收仓库：P1、P2 先用 llm-research-os 或 sand-table 自身。Vic. 掌握真实答案，"关键路径与人工核对一致"才能真正核对，也不会给外部维护者制造噪音。测试者仍应是非程序员。外部仓库放到 P3 之后。

## 8. 已接受的决定

本节与第 1–6 节的建议冲突时，以本节为准。例如问题 6 定下板子是瞬时状态，2.5 的持久化建议随之作废。

### 问题 1（2026-10-18）

先做工作台，不先做对外框架。目标是让这种交互方式能够取代对话框占主导的 AI 用法。

- 架构约束保留：核心不依赖某个宿主、某个 Agent、GitHub 或 Research OS 的业务类型。
- 产品交付后移：组件 SDK、配置迁移、嵌入示例和对外注册契约，等到第二个真实宿主再做。P1 不交付最小嵌入示例。
- 交互方式从第一天起不包含函数、提交、PR 等代码概念。它包括：指着白板上的对象说话，圈定 AI 的工作范围，AI 交回提案后由人接受、调整或拒绝，AI 收到的上下文可见、可改，工作结果留在空间里。
- 第二领域的纸面检查提前到 P0。用同一套交互走一遍非代码任务（例如比较两次研究实验）。走不通，就说明交互方式里混进了代码领域的假设。
- 验收增加纯对话对照组。同一个任务、同一个 Agent，分别用纯对话和 Sand Table 做，比较四项：有没有完成，发现了几次 AI 的错误，隔天找回上下文要多久，重复描述或复制粘贴了多少次。
- 简单一问一答仍用对话框。对话框从装下一切的主窗口，变成贴在白板某个位置上的输入框。

### 问题 2（2026-10-18）

不把不写引擎的幕布试验当作开工前提。P0 直接进入技术选型，并开始做第一个真实切片。

- 不做纸板白板、不招募非程序员、不设幕布后的人。
- 问题 1 已接受的纯对话对照和第二领域检查，改到第一个能用的版本上做。按问题 5，对照用外部任务，不用 Vic. 自己的项目。
- 交互方式是否真能取代对话框，以那个版本上的对照结果为准。这个证据因此来得更晚。

### 问题 3（2026-10-18）

Sand Table 是一个 MCP 服务器，加上一块用 MCP App 画出来的板子。分发时包进各家已经有的插件格式（Cursor、Claude Code、Codex 能安装的那种）。不给每个 harness 写一套界面插件，也不做 DeepSeek Harness 那种换掉会话视图的插件。

- 选择理由是推广：用户已经订着 Claude、ChatGPT、Cursor、Copilot。插件负责装进这些订阅，MCP 负责工具和板子。
- 各家插件的共同标准是技能和 MCP 服务器。斜杠命令、钩子、界面不在这份标准里。DeepSeek Harness 能在网页会话中间注册自己的视图，这个能力别的 harness 没有（此说法不准确，VS Code 与 Cursor 扩展也能开自己的视图，见 9.1）。
- 会画 MCP App 的宿主里出现板子。Claude、ChatGPT、Copilot 可以全屏；Cursor 只有行内。Claude Code 命令行和 Codex 不画这块界面时，仍然提供工具和文字。
- 这收窄了问题 1 里“人站在白板前、对话框贴在白板上”的摆法。人站在已经订着的对话里，板子是这场对话中的一块界面。输入框仍是宿主的输入框。

### 问题 4（2026-10-18）

社区贡献先不是提交功能。用已经合并过的 Issue 和 PR 做一场不公开的考试：仓库停在修好之前的版本，Sand Table 在这个版本上做一遍，和当时的结果做双盲比较。两边都不发到 GitHub。

- 做的时候不能看见后来的答案。提交钉在合并之前，也不去搜已经公开的那份 PR。题目事先选定，并记下“模型可能已经见过著名题目”的风险。
- 两份结果收成同一种东西再给评分的人看，例如一段修改加上一份给维护者的说明。一边是白板、一边是 GitHub 页面，盲就不成立。
- 评分标准事先写好。看有没有修好报告里的行为、改动有没有越界、维护者能不能看懂。不看和当时合并的那份像不像。
- 这场考试回答“做得好不好”。板子有没有比对话框好，仍用问题 1 的对照：同一个任务、同一个 Agent，一个用板子，一个只用对话。
- 开发计划里的 P5“准备并提交 PR”不再是当前产品功能。

以后如果真的提交到别人的仓库，不做门槛，Issue 和 PR 都可以。提交前的检查是一个开关，默认关着，用户自己选择用不用。打开时，对外草稿要先答三问，有一问答不上来就不生成草稿：实际发生了什么；这是观察到的，还是为了提交摆出来的；维护者追问当时的情况时，能不能不编造地回答。关掉时，按用户要的 Issue 或 PR 直接生成草稿。开关不管本地修改。草稿和真正发出去仍是两个动作，发出去要用户自己按发送。

### 问题 5（2026-10-18）

验收全部用外部仓库。不用 llm-research-os，也不用 sand-table 自己当验收对象。

板子说得对不对，也用这些外部题目判断：版本钉在修好之前，和当时的结果做双盲比较。不靠对自己项目的了解来认出假解释。题目事先选定并封存。验收不往这些仓库发送任何东西。

### 问题 6（2026-10-18）

不把板子写进 Research OS 的研究记录，Sand Table 自己也不做一本持久的账。板子是瞬时状态。

- 这次显示里，一句话仍然可以标出是谁说的、依据哪段代码、是确认过的还是猜的。界面关掉或这场交互结束，这些内容不保留。

### 改动由谁落笔（2026-10-18）

仓库里的改动都由 AI 写入。人不用一次说清，可以用一连串混合表述来提示，例如拖拽组件再加上一段文字。这些动作形成一份 diff。AI 查看这份 diff 来理解意图，整理出目标版本，向人确认这是不是他的意图，再写入。人的动作本身不直接改文件。

版本留在 git 里。Sand Table 不为这些改动再记一本账。这和问题 6 的瞬时板子并列：板子关掉就没了，留下的修改在 git 里。

## 9. 第 8 节之后的补充意见（2026-10-18，待 Vic. 决定）

以下不是已接受的决定。

### 9.1 第一问的目标被第三、六问降级了

第一问的目标是取代对话框为主的用法。第三问把板子放进对话里，第六问让它关掉就没。合起来，板子是对话里一块会被刷上去、关掉就消失的界面。这仍是对话框为主。

更正：讨论第三问时说过"能在会话中间挂自己视图的能力，别的 harness 没有"。这不准确。VS Code 和 Cursor 的扩展可以用 webview 开一整块编辑器标签页，也可以把 MCP 服务器注册给 Agent（VS Code：`vscode.lm.registerMcpServerDefinitionProvider`；Cursor：`vscode.cursor.mcp.registerServer`）。

建议：同一个 MCP 服务器，两种呈现。

- 在 Claude、ChatGPT、Copilot 的对话里，用 MCP App 呈现，负责推广；能全屏的宿主默认请求全屏。
- 在 Cursor 和 VS Code 里，用一个扩展把板子开成编辑器标签页，并把同一个 MCP 服务器注册给 Agent。人站在板子前，对话在侧边。仍然用用户已有的订阅，不另做 Agent 运行时。

Cursor 目前只把 MCP App 画在对话行内。第一个切片若在 Cursor 里做，扩展这一面才让人真正站在板子前。

板子把人的改动交给 Agent，用"拉"而不是"推"：人的改动留在 MCP 服务器的内存里，Agent 调用一个工具读取。这样不依赖宿主是否支持界面主动发消息，每个宿主都能用。

### 9.2 板子是 git 的投影

第六问（不记账）和第八节"改动由谁落笔"合起来，最强的读法是：板子是从当前 git 版本算出来的一张图；人在图上的改动是意图；AI 把意图变成代码；git 是唯一的状态。由此有三个后果。

1. **同一个版本必须算出同一张图。** 否则人的改动和图自己的变化混在一起，diff 没法读；隔天打开，图也会变样。代码结构用静态分析算；AI 写的说明按内容哈希缓存。缓存可以随时丢掉重算，不是账。
2. **不读代码也能验收。** AI 写完代码后，从新版本重新算一张图，和人改过的那张对比。对不上，说明 AI 没做到人要的。这是给非程序员的验收办法，也是我最想补上的一条。
3. **拖拽有两种意思。** 把一张卡拖进一个框，可能是"把这个函数搬到那个模块"，也可能只是"我想放在一起看"。原文 4.3 已经说过，靠近不等于依赖。建议把动作分成两类：整理（只为看，不交给 AI，关掉就没）和改动（交给 AI 当意图）。文字说明和 AI 的确认可以兜底，但不该靠它们来猜每一次拖拽。

问题 1 的对照里有一项"隔天找回上下文要多久"。按投影来读，代码结构隔天可以从 git 重新算出来，丢掉的只有整理和对话。要么接受这一项吃亏，要么允许把整理存成一个可丢弃的本地文件（例如放在 `.git/` 下、不进版本）。

### 9.3 考试设计

- **需要三组。** 当时高手的 PR；同一个操作者用同一个 Agent、只用对话；同一个操作者用同一个 Agent、用板子。没有只用对话那一组，"和高手比"量到的主要是模型。操作者是谁（非程序员，还是 Vic.）要事先定下。
- **不必从零出题。** SWE-bench 一类的题库已经把版本钉在修好之前，带运行环境和隐藏测试。担心模型见过题目，就用按时间收集新题的版本（例如 SWE-bench-Live、SWE-rebench），只取模型训练截止之后的题。具体版本和许可需要核对。隐藏测试给客观分；双盲评分看范围和可读性。
- **考试测的是修复，不是讲解。** 当时的 PR 里没有"这条路径怎么走"的讲解可比。问题 5 写的"板子说得对不对也用外部题目判断"，实际上判断不了讲解。建议两件事：每句讲解引用的代码，在当前版本上当场核对是否存在、是否一致（当场算，不留账）；评分的人再抽查一部分讲解。

第三问让第一个切片变小了：一个 MCP 服务器加一种呈现。在这个规模下，先做不写引擎的试验省下的成本也变小了。第 1.1 节的建议不再坚持。
